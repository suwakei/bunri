# 画面を自動操作してテストする

bunri の画面を、人の代わりにプログラム（Playwright）や Claude Code が操作して確かめる仕組み。

## 何を操作しているか

製品の形はデスクトップアプリだが、Playwright や Chrome DevTools が操作できるのは **ブラウザ** で、
Tauri アプリの窓（mac の WebView）には接続できない。そこで、同じ画面をブラウザで開く
「開発用のブラウザ起動」を相手にする。

```
ブラウザ (Chromium / WebKit) ──► Vite の開発サーバ (127.0.0.1:5199) ──/api──► API サーバ (空きポート、トークン無し)
```

`scripts/dev-web.mjs` がこの 2 つのサーバを起動して、止める。データ置き場は一時ディレクトリなので、
手元の `uploads/` `results/` `projects/` は汚れない。

**確かめられる範囲:** 画面の操作全般と、画面から API までの通し（ファイルの読み込み、解析、カルテ、
差分チェック、MIDI の書き出しなど）。

**確かめられない範囲:** ネイティブ側（Rust）の機能。API キーのキーチェーン保存、MIDI のネイティブ入力、
別窓、初回セットアップ、アプリの終了時の後始末。これらは `src-tauri` のテストで見る。

## 1. 決まった手順を自動で確かめる（Playwright のテスト）

```bash
cd web-ui && npx playwright install chromium webkit   # 初回のみ（ブラウザ本体を取得する）
make e2e
```

- テストは `web-ui/e2e/` に在る。サーバの起動と停止はテストが自分で行う
- ブラウザは 2 つで走る。Chromium と、デスクトップアプリの WebView に近い WebKit
- 失敗すると、スクリーンショットと操作の記録が `web-ui/e2e-results/` に残る
- 画面のポートは 5199。同じリポジトリの別の作業ツリー（git worktree）で同時に走らせるときは、
  `BUNRI_E2E_PORT=5197 make e2e` のように番号を変える（同じ番号だと、後から始めたほうが起動に失敗する）

いま在るテスト:

| ファイル | 確かめていること |
|---|---|
| `daw.spec.ts` | 初回の案内、トラックの追加、ピアノロールへのノート入力、MIDI の書き出し |
| `pianoroll.spec.ts` | ピアノロールのスクロールと長さ |
| `timeline.spec.ts` | タイムライン: 小節番号の段とクリップの位置、長い曲の横スクロール、シーク、トラックの追加と削除、クリップの削除とドロップ |
| `left-panel.spec.ts` | 左パネルのタブの切り替え、シンセ、ドラム、FX、ファイル読み込み、単音メロディ解析 |
| `header.spec.ts` | 保存と読込、WAV の書出、再生・一時停止・停止、メトロノーム、ステータスバー |
| `assistant.spec.ts` | AI のタブ（API の応答を差し替える。LLM は呼ばない） |
| `chart.spec.ts` | 音声ファイルの解析からカルテの表示まで |
| `coach.spec.ts` | お手本の重ね表示と差分チェック |
| `tools.spec.ts` | ツールの画面の WAV 情報、`../` を含むファイル名の拒否、使い方の画面 |
| `tools-tabs.spec.ts` | ツールの画面の編集、エフェクト、一括編集、音源合成、変換、解析 |

音は API サーバが実際に作る。テストは、返ってきた WAV の長さと振幅を読んで「指定どおりの長さで、
無音ではない」ことまで確かめている（`e2e/helpers.ts` の `readWav`）。
変換は ffmpeg が要る。無い環境では、その旨のエラーが画面に出ることを確かめる。
libfluidsynth と SoundFont が無い環境では、GM 音源は内蔵シンセで代替される。テストはどちらでも通る。

再現ガイドを本物の Claude で通すテスト（`e2e/guide.spec.ts`）だけは、普段は走らない。
API を実際に呼んで費用がかかるためで、`BUNRI_E2E_LLM=1` を付けたときだけ走る。
API キーは、環境変数（`ANTHROPIC_API_KEY` / `CLAUDE_API_KEY`）かリポジトリ直下の `.env` から読まれる。

```bash
cd web-ui && BUNRI_E2E_LLM=1 npx playwright test e2e/guide.spec.ts --project=chromium
```

## 2. Claude Code がその場で操作して確かめる（Playwright MCP）

リポジトリの `.mcp.json` に、Playwright の MCP サーバを登録してある。Claude Code をこのリポジトリで
起動し直すと、利用の許可を尋ねられる。許可すると、Claude Code が「ページを開く」「クリックする」
「入力する」「画面の構造を読む」「スクリーンショットを撮る」といった操作を使えるようになる。

手順:

1. 開発用のブラウザ起動を始める: `make dev-web`（準備ができると `{"event": "ready", "url": "http://127.0.0.1:5199", ...}` を出す）
2. Claude Code に、その URL を開いて確かめてほしいことを頼む
3. 終わったら `make dev-web` を Ctrl+C で止める

サーバの起動は、利用者が自分のターミナルで行うか、Claude Code に起動を頼む
（Claude Code は、頼まれない限り自分ではサーバを起動しない運用になっている）。

## 見つけた不具合の例

この仕組みを作る過程で、ブラウザを実際に操作して初めて分かった不具合が 3 つ在った。
単体テストはどれも通っていた。

- **シンセ以外のタブ（ドラム・FX・ファイル・カルテ・AI）の中身が表示されなかった。**
  CSS が `.panel-content` を `display: none` にしていて、`active` クラスを持つシンセのパネルだけが見えていた。
  React への移行のときから在った
- **開発モードで、最初のトラックが 4 本になっていた。** React の StrictMode で初期化が 2 回走るため
- **ピアノロールの見出しが、鍵盤とグリッドを右に押しやっていた。** 見出しが横並びの 1 列目になっていた

テストを残りの画面に広げたとき（左パネル、ヘッダ、ツールの各タブ）にも、同じ種類の不具合が見つかった。

- **ステータスバーが画面の下にはみ出して、見えていなかった。** 操作の結果やエラーはここに出るのに、
  高さの計算からステータスバーのぶん（28px）が抜けていた。最初の版から在った
- **セレクタに表示されているトラックと、実際に使われるトラックが違っていた。** FX は「Track 1」と
  表示しながら「クリップがありません」と断り、ファイル読み込みは「Track 1」と表示しながら末尾の
  トラックに入れていた
- **一括編集のトリム・カット・ループ・無音挿入が、必ず全部失敗していた。** React への移行のときに
  パラメータの入力欄が落ち、失敗の理由も表示されないので「0個成功」としか分からなかった

## テストを足すとき

- 画面の文言や構造が変わるとテストも変える必要が出るので、要素は役割（ボタン、ラベル）と表示の文で引く
- 初回の案内（ウェルカムガイド）は画面全体を覆う。普段のテストは `e2e/helpers.ts` の `openDaw()` で
  既読にしてから始める
- 音源分離や採譜など、時間のかかる処理は入れていない（数十秒〜数分かかり、モデルの取得も要るため）
- LLM を呼ぶ画面は、`page.route` で API の応答を差し替える。差し替えは画面を開く前に仕掛ける
  （開いた直後に飛ぶ呼び出しが在るため）
- ツールの画面の見出し（`<label>`）は入力欄と結び付いていないので、`getByLabel` では引けない。
  同じ枠（`.form-group`）の中の入力欄として引く（`e2e/tools-tabs.spec.ts` の `field`）
