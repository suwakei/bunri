# 画面を自動操作してテストする

bunri の画面を、人の代わりにプログラム（Playwright）や Claude Code が操作して確かめる仕組み。

## 何を操作しているか

自動操作のテストは 2 層ある。

| 層 | 相手 | コマンド | いつ回すか |
|---|---|---|---|
| ブラウザのテスト | 同じ画面をブラウザ (Chromium / WebKit) で開く「開発用のブラウザ起動」 | `make e2e` | 画面を触る変更のたび。数分 |
| 本物の窓のテスト | テスト用にビルドしたデスクトップアプリの窓 (WKWebView) | `make e2e-desktop` | CSP・フォント・同梱物・`tauri.conf.json`・`src-tauri/`・sidecar の起動や鍵・書き出しを変えたとき。2 回目以降は 20 秒ほど (初回はビルドで数分) |

```
ブラウザ (Chromium / WebKit) ──► Vite の開発サーバ (127.0.0.1:5199) ──/api──► API サーバ (空きポート、トークン無し)

テスト (vitest) ──WebDriver──► bunri (テスト用のビルド) の窓 ──► sidecar (空きポート、トークン付き) ──► 偽の Claude
```

ブラウザのテストは画面の操作を広く細かく見る。本物の窓のテストは、ブラウザでは確かめられないこと
(WKWebView、`tauri://localhost`、トークン、同梱したフォント、ネイティブ側の動き) だけを短く見る。

### ブラウザのテストの相手

`scripts/dev-web.mjs` が Vite の開発サーバと API サーバを起動して、止める。データ置き場は一時ディレクトリなので、
手元の `uploads/` `results/` `projects/` は汚れない。

画面には **デスクトップアプリと同じ CSP** を掛ける (`src-tauri/tauri.conf.json` から起動のたびに読む。
`scripts/desktop-csp.mjs`)。足しているのは、Vite が埋め込むスクリプトの nonce、自動再読み込みの接続 (`ws:`)、
違反の知らせ先 (`report-uri`) だけ。開発サーバの自動再読み込みの仕組み (`@vite/client`) が blob の worker を止められた違反だけは数えない (接続が切れたときに blob の SharedWorker でつなぎ直せるかを確かめる。デスクトップアプリには入っていない。テストがページを閉じたときや、この Mac が休止に近い状態になると、main でも出ていた)。出どころ・種類・止めたもの (blob) が全部合うものだけを除き、`@vite/client` のほかの違反やアプリ自身の worker の違反は数える。違反はブラウザから開発サーバに届き、**どのテストの途中で起きた違反でも、
最後にまとめて失敗になる** (`e2e/csp-check.ts`)。失敗の文に、止められた URL とページが出る。
デスクトップアプリでは、CSP に止められたもの (フォント、音声、API の呼び出し) は黙って読み込まれないので、
ここで先に見つける。

**確かめられる範囲:** 画面の操作全般と、画面から API までの通し（ファイルの読み込み、解析、カルテ、
差分チェック、MIDI の書き出しなど）。CSP の違反。

**確かめられない範囲:** 本物の窓 (WKWebView) とネイティブ側（Rust）の機能。これは本物の窓のテスト (3.) と
`src-tauri` のテストで見る。再生は、ブラウザでは Web Audio の経路だけを通る (デスクトップ版は Rust の engine が鳴らす)。
Rust に渡す口 (`lib/native-audio.ts`) は、Vitest が `__TAURI__` を偽物にして確かめる (`__tests__/native-audio.test.ts`)。プロジェクトの保存・開くは、ブラウザでは名前を尋ねてデータ置き場の `projects/` に置く経路で通す
(デスクトップ版のダイアログと最近使ったプロジェクトの持ち方は Rust)。

## 1. 決まった手順を自動で確かめる（Playwright のテスト）

```bash
cd web-ui && npx playwright install chromium webkit   # 初回のみ（ブラウザ本体を取得する）
make e2e
```

- テストは `web-ui/e2e/` に在る。サーバの起動と停止はテストが自分で行う
- ブラウザは 2 つで走る。Chromium と、デスクトップアプリの WebView に近い WebKit
- 失敗すると、スクリーンショットと操作の記録が `web-ui/e2e-results/` に残る
- 画面のポートは 5199、偽の Claude サーバは 5198。同じリポジトリの別の作業ツリー（git worktree）で同時に走らせるときは、
  `BUNRI_E2E_PORT=5299 BUNRI_E2E_FAKE_LLM_PORT=5298 make e2e` のように両方の番号を変える（同じ番号だと、後から始めたほうが起動に失敗する）

音は API サーバが実際に作る。テストは、返ってきた WAV の長さと振幅を読んで「指定どおりの長さで、
無音ではない」ことまで確かめている（`e2e/helpers.ts` の `readWav`）。
変換は ffmpeg が要る。無い環境では、その旨のエラーが画面に出ることを確かめる。
libfluidsynth と SoundFont が無い環境では、GM 音源は内蔵シンセで代替される。テストはどちらでも通る。

再現ガイドは Claude の API を呼ぶ機能だが、普段のテストは **本物の Claude を呼ばない**。
`playwright.config.ts` が偽の Claude サーバ（`e2e/fake-anthropic.mjs`、127.0.0.1:5198）を起動し、
API サーバには環境変数 `ANTHROPIC_BASE_URL` でそちらを向かせる。アプリ側のコードには手を入れておらず、
公式 SDK がそのまま偽のサーバへリクエストを送る。手元の `.env` に本物の API キーが在っても、
環境変数のキー（偽の値）が優先されるので使われない。

偽のサーバは呼ばれた回数を数えているので、`e2e/guide-cost.spec.ts` は「Claude を呼んだか」を直接確かめる:
作ったガイドが保存され、開き直しても呼ばれないこと。作り直したときだけ呼ばれること。
1 日の上限に達していると、呼ばずに理由が画面に出ること。

偽のサーバは、差分の説明（第3層）にも応える（出力の形が `points` を持つかで見分ける）。送られてきた事実の
指摘の ID と小節を指す説明を返すので、`e2e/coach-explain.spec.ts` は、説明の場所の札から小節へ移れることまで確かめる。
`/__calls` の `explain` が、そのうち説明を作った回数。
事実に強さの違い（`velocity`。お手本が MIDI ファイルから読み込んだもののときだけ在る）が入っていれば、強さの点を 1 つ足して返す。
`e2e/coach-velocity.spec.ts` は、これで「強さの事実が Claude まで届いたか」を画面から確かめる。

時間のかかる処理（音源分離・パート分離）は数分かかるので、`e2e/jobs.spec.ts` は API サーバのテスト用の遅いジョブ
（`BUNRI_E2E_HOOKS=1` のときだけ在る。[jobs.md](jobs.md)「テスト用の遅いジョブ」）を使う。画面のボタンから始める流れは、
始めるリクエストを `page.route` で遅いジョブへ付け替えて確かめる。結果を決めて確かめたいとき（`learn.spec.ts`）は、
`e2e/helpers.ts` の `fakeJob` でジョブの応答そのものを差し替える。

再現ガイドを本物の Claude で通すテスト（`e2e/guide.spec.ts`）だけは、普段は走らない。
API を実際に呼んで費用がかかるためで、`BUNRI_E2E_LLM=1` を付けたときだけ走る（このときは偽のサーバを使わない）。
API キーは、環境変数（`ANTHROPIC_API_KEY` / `CLAUDE_API_KEY`）かリポジトリ直下の `.env` から読まれる。

```bash
cd web-ui && BUNRI_E2E_LLM=1 npx playwright test e2e/guide.spec.ts --project=chromium
```

## 2. Claude Code がその場で操作して確かめる（Playwright MCP）

リポジトリの `.mcp.json` に、Playwright の MCP サーバを登録してある。Claude Code をこのリポジトリで
起動し直すと、利用の許可を尋ねられる。許可すると、Claude Code が「ページを開く」「クリックする」
「入力する」「画面の構造を読む」「スクリーンショットを撮る」といった操作を使えるようになる。

手順:

1. 開発用のブラウザ起動を始める: `make dev-web`（準備ができると `{"event": "ready", "url": "http://127.0.0.1:5199", ...}` を出す）
2. Claude Code に、その URL を開いて確かめてほしいことを頼む
3. 終わったら `make dev-web` を Ctrl+C で止める

サーバの起動は、利用者が自分のターミナルで行うか、Claude Code に起動を頼む
（Claude Code は、頼まれない限り自分ではサーバを起動しない運用になっている）。

## 3. 本物の窓を自動操作する（make e2e-desktop）

```bash
make e2e-desktop     # = cd web-ui && npm run e2e:desktop
```

テスト用のビルド (Cargo の機能 `e2e`) のアプリを起動し、アプリの中で動く WebDriver サーバ
(`tauri-plugin-wdio-webdriver`) を通して、本物の窓を操作する。mac だけで動く。

やっていること:

1. **ビルド** (`web-ui/e2e-desktop/build.mjs`): `tauri build --debug --no-bundle --features e2e`。配布物と同じく
   画面を同梱して `tauri://localhost` で出す (CSP も同じ)。出力は `src-tauri/target/e2e/`
   (開発用の `tauri dev` のビルドとは分けてある)。初回は数分、2 回目からは数秒
2. **起動** (`web-ui/e2e-desktop/launch.ts`): 利用者のデータから切り離して起動する。データ置き場と書き出しの保存先は
   一時ディレクトリ、WebView の保存領域は使い捨て、Claude は偽のサーバ、API キーは偽の値 (キーチェーンは読まない)、
   ポートはすべて空いている番号。手元で bunri が動いていてもぶつからない
3. **テスト** (`web-ui/e2e-desktop/smoke.test.ts`。vitest で書いてある)
4. **後片付け**: 窓を閉じて (利用者が閉じたときと同じ終わり方) アプリを終わらせ、**sidecar まで終わったことを確かめる**。
   残っていたら止めて失敗にする。一時ディレクトリは消す (`BUNRI_E2E_KEEP=1` で残せる)

アプリの出力は `web-ui/e2e-desktop-results/app.log`、最後の窓の画像は `last-window.png` に残る。

いま在るテスト (`smoke.test.ts`):

| 確かめていること | なぜ本物の窓で見るか |
|---|---|
| 同梱した画面が `tauri://localhost` で出て、起動の表示が消え、`boot_status` が待ち受け中になる | sidecar の起動と、画面への接続情報の受け渡しは、デスクトップ版にしか無い |
| データ置き場が空でも案内を出さず、編集画面とトラック追加を使える | |
| 起動から最後まで、CSP の違反も、捕まえられなかった例外も無い (`window.__bunriE2E`。画面の読み込みより前から記録する) | 本物の CSP は Tauri が掛ける (ハッシュや nonce を足す)。ブラウザの写しとずれていないかの最後の確認 |
| CSP が実際に効いている (許していない読み込みが止まる) | 「違反が無い」が、CSP が効いていないせいではないことの確認 |
| 同梱したフォント (Outfit / IBM Plex Mono) の全部の書体が読み込め、画面がそのフォントで描かれる | WKWebView と `tauri://` で配られるフォントは、ブラウザでは確かめられない |
| トークン無し・違うトークンの API 呼び出しは 401、正しいトークンなら `tauri://localhost` から呼べる (CORS) | 鍵は、デスクトップ版でだけ掛かる |
| `<audio src>` は、クエリのトークンで sidecar の音声を読める (トークン無しでは読めない) | `media-src` と、ヘッダを付けられない経路の鍵 |
| WAV をタイムラインに置くとクリップが出て、再生すると再生位置が進み、停止できる | 再生が実際に動くか。出力デバイスの在る機械では Rust の engine (クリップの音声を Rust へ送る経路を含む)、無い機械では WKWebView の Web Audio を通る |
| ノートを置いて再生すると再生位置が進み、止めると止まる | ノートの再生。Rust の engine でも、Web Audio に切り替わっていても通る書き方 (どちらで鳴らしたかは、アプリのログに出す) |
| WAV の書き出しで、ファイルが保存される (長さと振幅も確かめる) | WKWebView の `<a download>` (blob) の保存は、ブラウザとは別の仕組み (Rust の `on_download`) を通る |
| カルテを作って再現ガイドを頼むと、sidecar が (偽の) Claude を呼んでガイドが返る | `tauri://localhost` → sidecar (トークン、CORS、`connect-src`) → Claude の通し |
| 押したボタンとその結果が、時刻つきで動きの記録のファイルに残る。エージェントが足した行も同じ並びに入り、「記録」の一覧にも出る。sidecar のトークンは残らない | 記録のファイルは、ネイティブ側 (Rust の `activity.rs`) が書く。ブラウザには無い |
| アシスタントに頼むと、(偽の) Claude がツールを呼び、操作ログの行が出て、トラックとノートが増える。動きの記録に残り、1 回で元に戻る。再生を頼むと再生位置が進む。WAV の書き出しを頼むとファイルが保存される | `tauri://localhost` → sidecar → Claude の、少しずつ届く応答 (ストリーミング) を WKWebView で読めるか。利用者の操作の外から始めた再生・保存が、本物の窓で通るか |
| 押せるものを名前で探して操作できる (一覧、見つからないときの説明、キー) | エージェントが窓を操作するときの部品 (`e2e-desktop/controls.ts`) が、本物の窓で動くか |
| MIDI 入力を開いたあとに作った仮想の MIDI ポート (`e2e-desktop/virtual-midi.swift`) が「再検出」で見つかり、鍵盤 1 回が 1 回だけ届く (作れない環境では飛ばす) | OS の MIDI (CoreMIDI) を通る経路は、ブラウザには無い。あとからつないだ機器が見えるかは、アプリが最初の MIDI クライアントをどのスレッドで作ったかで決まる |
| sidecar を止める (テストが起動したアプリの sidecar だけ) と、止まったことの知らせが出て、「再起動」で新しいポートとトークンの sidecar に差し替わる。トラックはそのまま残る | sidecar の起動し直し (Rust の `restart_backend`) と、新しい接続情報の受け渡しは、デスクトップ版にしか無い |

**確かめられない範囲** (テスト用のビルドの事情):

- **初回セットアップ** (アプリのデータ置き場への `uv sync`)。テスト用のビルドは、sidecar を開発時と同じく
  リポジトリの `uv run` で起動する。セットアップの流れは `src-tauri` のテスト (`sidecar.rs`) で見ている
- **別窓 (ツール・使い方)、ファイルを選ぶ画面、マイクの許可の確認。** WebDriver のプラグインが、WKWebView の
  UI の受け手 (WKUIDelegate) を自分のものに差し替えるため、テスト用のビルドではこれらが配布物と同じには動かない
- **キーチェーン、MIDI のネイティブ入力。** 利用者のキーチェーンに触れないよう、テストでは使わない。
  `cargo test -- --ignored` の手で回すテストで見る
- **クリックは画面の中の `element.click()`** で、OS のマウス操作ではない。ドラッグなど細かな操作はブラウザのテストで見る
- **書き出しの保存先**: テストでは一時ディレクトリに差し替える。`~/Downloads` に保存されることそのものは見ていない
- **プロジェクトの保存・開くのダイアログ**: ネイティブのダイアログ (NSSavePanel / NSOpenPanel) は WebDriver で操作できない。
  テスト用のビルドだけ、ダイアログを出さずに環境変数 `BUNRI_E2E_SAVE_PATH` / `BUNRI_E2E_OPEN_PATH` の場所が選ばれたことにする
  (`src-tauri/src/e2e.rs` の `dialog_path`。テストは一時ディレクトリの中を渡す)。ダイアログそのもの (既定の場所が「書類」の
  bunri フォルダになる、拡張子の絞り込み) は手で確かめる。写してよい場所の確かめ・最近使ったプロジェクト・閉じる前の確かめは
  配布物と同じに動く (窓を閉じる要求は WebDriver の「窓を閉じる」で送る)
- 画面の細かな操作。タブの並びなどの画面の構造には深く依存させていない (ブラウザのテストの役目)

CI では自動で走らない (CI はビルドの確認だけにしている)。Actions の画面から手で起動したときだけ、
mac のランナーで走る (`.github/workflows/desktop-e2e.yml`)。ふだんは手元で `make e2e-desktop` を回す。
依存は `uv sync --frozen` で全部入れる (sidecar の起動に使う `uv run` が、抜いた依存を入れ直すため)。
あわせて、配布物の設定に WebDriver サーバが入らないことも確かめる (docs/desktop-architecture.md「窓を自動操作するテスト」)。

## 4. 頼まれた操作を行い、動きの記録で追う（Claude Code 向け）

利用者がチャットで「こう操作して」「こう操作したらこうなった」と言ったときに、エージェントが本物の窓を操作し、
**いま何をして、そのあと何が起きたか** を確かめるための仕組み。手順は `.claude/skills/drive/SKILL.md`（`/drive`）。

### 動きの記録

アプリは、起きたことを起きた順に 1 行ずつ残す（`web-ui/src/lib/activity.ts`、`src-tauri/src/activity.rs`）。

```
18:42:07.311 [agent] 「MIDI 入力」を押す
18:42:07.318 [click] ボタン「MIDI 入力」
18:42:07.352 [midi-in] 開いたポート: SINCO SMK25-Master / SMK25V2 Bluetooth
18:42:07.360 [midi] MIDI 入力を開いた（SINCO SMK25-Master / SMK25V2 Bluetooth）
18:42:11.904 [midi-in] SINCO SMK25-Master: note-on ch1 60(C4) vel 96
18:42:11.906 [midi] 押した C4（強さ 96）
```

| 札 | 載るもの |
|---|---|
| `app` | 起動（日付と版） |
| `click` `change` `key` | 画面の操作。どのボタン・どの欄か（画面全体で拾うので、部品ごとに書かなくてよい） |
| `status` | ステータスバーの文（操作の結果とエラーは、ここに出る） |
| `api` | 処理を担当する部分の呼び出しと、結果の番号・かかった時間（数秒おきの見張りと進み具合の問い合わせは、失敗したときだけ） |
| `midi` | MIDI 入力のつなぎ、鍵盤の操作、置いたノート |
| `midi-in` | 鍵盤から届いたメッセージ。**ポートの名前つき**（ネイティブ側が足す。つまみのように続くものは間引く） |
| `error` | 捕まえられなかった例外 |
| `agent` | エージェントが行った操作（「いまから何をするか」） |

- **利用者が見るための記録**でもある。ステータスバーの「記録」で、同じ内容を時刻つきで見られる。
  エージェントが足した行（`agent`）もそこに出るので、利用者は、いま何を操作されているかを画面で追える
- デスクトップ版は、同じ内容をファイルにも残す。置き場は、データ置き場の `logs/activity.log`:
  開発時（`make desktop`）は **リポジトリ直下の `logs/activity.log`**、配布物は
  `~/Library/Application Support/<識別子>/data/logs/activity.log`、テスト用のビルドは一時ディレクトリの中。
  1 MB を超えていたら、起動のときに `activity.1.log` へ回す
- 開発用のブラウザ起動では、画面の中にだけ残る（ファイルは無い）
- **載せないもの**: 入力欄に打っている途中の文字、API キー、sidecar のトークン、API に送った中身・返ってきた中身、
  API のクエリの値（`?name=…` のように名前だけ残す。`async` は値も残す）。
  文字を打つ欄は「値は記録しません」とだけ残し、選択肢・チェック・数値は選んだものを残す
- **載るもの**: プロジェクト・トラック・ファイルの名前。結果の文（「プロジェクト「〜」を保存しました」）、ボタンの名前
  （「「〜」のメニュー」）、API のパス（`/api/download/〜.wav`）として載る。何を操作したのかが分からないと、記録として役に立たないため
- 同じエラーが続けて来たとき（毎フレーム投げられる例外など）は、最初の 1 行と回数にまとめる
- 別窓（ツール・使い方）での操作は、ファイルには残るが、メインの窓の「記録」の一覧には出ない（一覧は窓ごと）。
  ツールの画面の結果の文は、ステータスバーを通らないので `status` の行にならない（`click` と `api` の行は残る）

新しい機能を足すとき、操作と、DAW の画面の結果（`setStatus`）と、API の呼び出しは、何もしなくても記録に残る。
画面にも API にも出ない出来事（MIDI のように外から届くもの）だけ、`recordActivity(札, 文)` を足す。

### 利用者が自分で操作した結果を追う

利用者が自分のターミナルで `make desktop` を動かしていれば、エージェントは `logs/activity.log` を読むだけでよい
（本物の鍵盤、マイク、利用者のプロジェクトを使う確認は、こちら）。

```bash
node web-ui/e2e-desktop/drive.ts log --dev                 # 前に読んだところから先
node web-ui/e2e-desktop/drive.ts wait-log 'midi-in.*note-on' --dev --timeout 120   # その行が出るまで待つ
```

利用者の `make desktop` の窓を、エージェントが操作することはできない。外から操作する口（WebDriver サーバ）は、
テスト用のビルドにしか入れていないため（docs/desktop-architecture.md「窓を自動操作するテスト」）。

### エージェントが操作する

```bash
cd web-ui && npm run desktop:inspect          # 裏で起動する。初回はビルドに数分
node web-ui/e2e-desktop/drive.ts wait-ready   # 窓の準備ができるまで待つ
node web-ui/e2e-desktop/drive.ts ui           # いま押せるものの一覧（画面のことば）と、ステータスバーの文
node web-ui/e2e-desktop/drive.ts click "MIDI 入力"
node web-ui/e2e-desktop/drive.ts set "録り方" "ステップ入力"
node web-ui/e2e-desktop/drive.ts key Space
node web-ui/e2e-desktop/drive.ts shot         # 窓の画像を保存して、場所を出す
node web-ui/e2e-desktop/drive.ts stop         # 窓を閉じ、アプリ・sidecar・偽の Claude サーバを止める
```

`npm run desktop:inspect` は、テストと同じく切り離した状態でアプリを起動し、WebDriver のセッションの情報を
`web-ui/e2e-desktop-results/session.json` に書く（同じ内容を 1 行の JSON でも出す）。`drive.ts` はそれを読んでつなぐ。

`click` `set` `key` は、1 回の呼び出しで次のことをする: 記録に `agent` の行を足す → 操作する → 少し待つ →
そのあいだに記録に増えた行と、ステータスバーの文を出す。押すものは、セレクタではなく画面のことば（ボタンの文、
欄の名前）で指す。同じ名前が 2 つ以上あるときは勝手に選ばず、`--nth N` を求める（`e2e-desktop/controls.ts`）。
操作できなかったとき（名前が見つからない、など）は、その旨の `agent` の行も足す。

`wait-log <正規表現>` は、記録に当てはまる行が出るまで待つ。前に読んだところから先を見る
（まだ一度も読んでいない記録では、いまより後に出た行だけ）。操作のコマンドは、そのあと増えた行を読んだことにするので、
操作の結果として出る行を待つときは `--since-action` を付ける（直前の操作の行から先を見る）。
読んだ位置は、ファイルの頭の行と一緒に覚えている（`e2e-desktop/reader.ts`）。同じ名前のファイルが別の中身に替わったら、頭から読む。

- サーバの起動にあたるので、Claude Code は頼まれたときだけ使う。`.mcp.json` には登録していない
- 利用者のデータには触れない（データ置き場・書き出し先・キーチェーンの項目は、テストと同じく別のもの）。Claude は偽のサーバ
- できないことは「確かめられない範囲」と同じ。クリックは画面の中の `element.click()` なので、ドラッグや
  ピアノロールのキャンバスの上の細かな操作はできない（`drive.ts eval` で JavaScript を実行するか、ブラウザの Playwright MCP を使う）
- W3C WebDriver の API を直接送ることもできる（`curl -s <session>/screenshot | jq -r .value | base64 -d > window.png`）

## 見つけた不具合の例

この仕組みを作る過程で、ブラウザを実際に操作して初めて分かった不具合が 3 つ在った。
単体テストはどれも通っていた。

- **シンセ以外のタブ（ドラム・FX・ファイル・カルテ・AI）の中身が表示されなかった。**
  CSS が `.panel-content` を `display: none` にしていて、`active` クラスを持つシンセのパネルだけが見えていた。
  React への移行のときから在った
- **開発モードで、最初のトラックが 4 本になっていた。** React の StrictMode で初期化が 2 回走るため
- **ピアノロールの見出しが、鍵盤とグリッドを右に押しやっていた。** 見出しが横並びの 1 列目になっていた

テストを残りの画面に広げたとき（左パネル、ヘッダ、ツールの各タブ）にも、同じ種類の不具合が見つかった。

- **ステータスバーが画面の下にはみ出して、見えていなかった。** 操作の結果やエラーはここに出るのに、
  高さの計算からステータスバーのぶん（28px）が抜けていた。最初の版から在った
- **セレクタに表示されているトラックと、実際に使われるトラックが違っていた。** FX は「Track 1」と
  表示しながら「クリップがありません」と断り、ファイル読み込みは「Track 1」と表示しながら末尾の
  トラックに入れていた
- **一括編集のトリム・カット・ループ・無音挿入が、必ず全部失敗していた。** React への移行のときに
  パラメータの入力欄が落ち、失敗の理由も表示されないので「0個成功」としか分からなかった

## テストを足すとき

- 画面の文言や構造が変わるとテストも変える必要が出るので、要素は役割（ボタン、ラベル）と表示の文で引く
- 案内（ウェルカムガイド）は使い方から `/?guide=1` で開いたときだけ画面を覆う。通常起動では表示しない
- `openDaw()` は、自動保存（`lib/autosave.ts`）も止める。保存していない変更のまま 30 秒経つと復旧用の写しが残り、
  データ置き場は全部のテストで共有なので、後のテストの起動で「前回、保存していない変更が残っています」の窓が出てしまうため。
  止める・間隔を変える口は、ブラウザの保存領域の `bunri-autosave`（`off` か `{"idleMs": 400, "maxWaitMs": 4000}` のような JSON）。
  自動保存を確かめるテスト（`autosave.spec.ts`）は `openDaw(page, { autosave: {...} })` で短い間隔にし、テストの前後で
  復旧用の写しを消す（`DELETE /api/project/recovery`）。`page.goto('/')` で直接開くテストは自動保存が動くので、
  保存していない変更のまま 30 秒以上置かない
- 音源分離や採譜など、時間のかかる処理は入れていない（数十秒〜数分かかり、モデルの取得も要るため）。
  パート分離を通す画面のテスト（`learn.spec.ts`）は、`/api/decompose` のジョブの応答を `fakeJob` で差し替える。
  時間のかかる API は `?async=1` のジョブとして始まるので、終わるのを待つときは `runJob(page, path, 操作)` を使う
  （`waitForResponse` で始めの応答を待っても、それは 202 で、結果ではない）
- 起動したときはトラックが無い。トラックを使うテストは `e2e/helpers.ts` の `startFree(page)`（「+ トラック追加」で
  Track 1・Track 2 を作り、最初のトラックと音作りを開く）で用意する。曲の取り込みは `importSong(page, file)`（原曲のファイルの欄に渡す）。
  WAV 以外の曲は `e2e/fixtures/song.mp3`（`SONG_MP3`。8 秒）
- LLM を呼ぶ画面は、`page.route` で API の応答を差し替える。差し替えは画面を開く前に仕掛ける
  （開いた直後に飛ぶ呼び出しが在るため）
- ツールの画面の見出し（`<label>`）は入力欄と結び付いていないので、`getByLabel` では引けない。
  同じ枠（`.form-group`）の中の入力欄として引く（`e2e/tools-tabs.spec.ts` の `field`）。
  DAW の画面の左パネルとヘッダは結び付けてあるので、`getByLabel('小節数')` のように引ける
- 左パネルのタブは `role="tab"`（`e2e/helpers.ts` の `openTab`。「カルテ」「シンセ」のような中の段の名前を渡すと、上の段のタブも開く）。トラックの M・S・メニューは、
  `getByRole('button', { name: '「Track 1」をミュート' })` / `'「Track 1」のメニュー'` のように名前で引ける。トラックを消すのは
  `e2e/helpers.ts` の `deleteTrack(page, 'Track 1')`（メニューの「トラックを削除」）。音量とパンは `getByRole('slider', { name: '「Track 1」の音量' })`
- ショートカットは `page.keyboard.press('ControlOrMeta+z')` のように書く（mac では Cmd、それ以外では Ctrl になる。アプリはどちらも受ける）
- 音が鳴ったかどうかは、`e2e/helpers.ts` の `recordOscillators` で確かめられる
  （鳴らされたオシレータの周波数を記録する。画面を開く前に仕掛ける）
- 画面の文を変えるときは、先に [ui-terms.md](ui-terms.md)（ことばの決まり）を見る
- 本物の窓のテストに足すのは、ブラウザでは確かめられないことだけにする (起動に時間がかかり、mac でしか動かないため)。
  画面の中で確かめる処理は `app.run(() => ...)` で書く (関数は文字列にして窓に送られるので、外の変数は引数で渡す)
