# 再現ガイド（第2層）設計

楽曲カルテ（第1層）を「こう作れば再現できる」という手順の説明にする層。
製品方針と 3 層構成は [song-chart-design.md](song-chart-design.md) を参照。

> **この文書の決定は暫定。** 第1層の設計は設計セッションで詰めたが、第2層は
> 「いま実装できるものを進めてよい」との指示で、未決だった項目を実装者の判断で埋めた。
> 下の表の各項目は、見直してよい前提で書いてある。

## 原則の守り方

**DSP が事実を出し、LLM は言語化だけをする。LLM は音符を 1 つも出力しない。**
これを、指示文だけでなく仕組みで守る。

| 仕組み | 何を防ぐか |
|---|---|
| LLM に渡すのはカルテだけ（音声は渡さない） | LLM が自分で「聴いて」事実を足すこと |
| 出力の形を Structured Outputs で固定する。持てるのは説明文と、場所への参照（セクション ID、小節・拍）だけ | 音符のデータを返すこと。形の上で入れる場所が無い |
| 参照をカルテと突き合わせ、実在しない場所を指すものは落とす | 存在しない小節へのハイライト |
| 説明文に出てきた音名・コード名のうち、カルテに無いものを「未確認の語」として返す | カルテに無い事実（コード、具体的な音高）を説明文に紛れ込ませること |

最後の仕組みは見張りであって、遮断ではない。「A メロ」の A のような誤検出がありうるので、
出力は捨てず、画面が「解析結果に無い語が含まれている。モデルの推測かもしれない」と示す。

## 第1層で後送りにした項目と、今回の決定

| 項目 | 決定 | 理由 |
|---|---|---|
| API キーの持ち方 | 呼び出しのたびに読む。入手先は 設定画面 → 環境変数（`ANTHROPIC_API_KEY`、無ければ `CLAUDE_API_KEY`）→ 開発時はリポジトリ直下の `.env` → SDK の既定の解決 の順。デスクトップ版は OS のキーチェーンに保存し、起動時に sidecar へ環境変数で渡す | 配布物に同梱できない。import 時に固めると起動後に設定したキーを拾えない |
| モデル | `claude-opus-5-5`。環境変数 `BUNRI_GUIDE_MODEL` で差し替えられる | 既定は現行の Opus。費用を抑えたい場合は利用者が差し替える |
| Structured Outputs の形 | `overview` / `steps[]`（`title` `topic` `body` `refs[]`）/ `cautions[]` | 上の「原則の守り方」のとおり |
| 応答言語 | 日本語 | 画面が日本語 |
| プロンプトキャッシュ | 指示文とカルテを `system` に置き、カルテの後ろに区切りを打つ。問い合わせごとに変わる対象（`focus`）は `user` に置く。保持時間は既定の 5 分 | 1 曲のカルテに対して、対象を変えて何度か問い合わせる使われ方。カルテは `to_canonical_json` でバイト安定。詳しくは下の「費用」 |
| 既存 `music_assistant.py` の作り直し | **していない** | 既存のアシスタントは音符を生成する作りで、原則と逆向き。置き換えるか残すかは製品の判断なので触っていない。再現ガイドは別モジュールで、公式 SDK だけを使う |

そのほかの決定:

- **LLM に渡すのは、カルテのうち言語化に使う項目だけ。** 外す項目と理由は下の「費用」の表
- **思考の深さは `low` に固定。** 確信度をコードの側で 3 段階に直して渡すようにしたうえで、low でも内容の
  誤りが出ないことを実測で確かめた（下の「費用」）。それまでは `medium`
- **安全性の分類器が応答を断ったときは、サーバ側で別のモデルに回す**（`fallbacks: "default"`）
- **Claude のみ。** ローカル LLM（Ollama）には対応していない。ローカル完結は要件から外れている
- **ガイドは保存する。** 同じ条件なら Claude を呼ばずに返す。作り直すのは、利用者が明示的に押したときだけ
  （下の「費用」）

## 利用者に見せること

- カルテ（解析結果）を Anthropic に送ること、音声とファイル名は送らないことを、作る前に画面に出す
- Claude を呼ぶと費用がかかること。作り直しのボタンに「費用がかかります」と添え、1 回ごとのトークン数と
  概算の費用、今日の累計と上限を出す
- 確信度が低い項目・検出できなかった項目は、`cautions` として分けて見せる
- `grid.user_confirmed` が false のときは、最初の手順でテンポと 1 拍目の確認を促す
  （倍・半分にずれていると、コードもセクションも全部ずれるため）

## 費用 — Claude を無駄に呼ばないための仕組み

再現ガイドは、1 回作るたびに Claude の API の費用がかかる（下の実測で、1 回 0.06〜0.22 ドル）。
利用者のクレジットを無駄にしないよう、次の仕組みを入れてある。上から順に効果が大きい。

| 仕組み | 何をするか | どこ |
|---|---|---|
| ガイドの保存 | 作ったガイドを保存し、同じ条件なら Claude を呼ばずに返す。画面は、保存済みが在れば最初から表示する | `guide_cache.py`、`reproduction_guide.guide_for` |
| 同時に走らせない | 同じカルテへの呼び出しを 1 つずつ通す。待っている間に同じ条件のガイドが出来たら、それを返す | `guide_cache.lock_for` |
| 材料が足りなければ呼ばない | テンポ・キー・コード・構成・ミックスのうち、解析できた項目が 1 つ以下なら、呼ばずに短く断る | `material_shortage` |
| 1 日の上限 | その日に呼んだ回数（か概算の費用）が上限に達していたら、呼ばずに理由を出す。既定は 20 回 | `guide_usage.today` |
| 入力を絞る | カルテのうち、言語化に使う項目だけを、詰めた形で渡す | `prompt_chart` |
| 入力の量の確認 | 上限（既定 30,000 トークン）を超える長いカルテは、黙って切らず、対象をセクションに絞らせる | `fit_request` |
| 出力を絞る | 書く量の目安（手順の数、1 手順の長さ）を、例つきで指示文に書く | `SYSTEM_PROMPT` |
| プロンプトキャッシュ | 同じカルテに、対象を変えて続けて問い合わせたとき、指示文とカルテのぶんを割引で読む | `build_request` |
| 使用量の記録と表示 | 呼び出しごとにトークン数と概算の費用を記録し、画面に 1 回ごとの量と今日の累計を出す | `guide_usage.py`、`GuidePanel.tsx` |

### ガイドの保存

- **鍵:** カルテの正規化 JSON（`song_chart.to_canonical_json`）のハッシュ + 対象 + モデル + 思考の深さ +
  指示文と出力の形の指紋。どれか 1 つでも違えば、保存分は使われない
- **版:** 指示文・出力の形・カルテの渡し方・検証を変えたら `GUIDE_VERSION` を上げる。指示文と出力の形は、
  上げ忘れても指紋が変わるので、古い保存分が使われることは無い。カルテの渡し方（`prompt_chart`）と
  検証（`validate_guide`）は指紋に入らないので、変えたら必ず版を上げる
- **置き場:** `results/guide/cache/<鍵>.json`。グリッドを補正するとカルテが変わるので、別の鍵になる
- **作り直し:** 画面の「ガイドを作り直す（費用がかかります）」を押したときだけ。保存分を置き換える
- **同時実行:** 連打や二重送信では、あとから来たほうが先のものを待ち、出来た保存分を受け取る（作り直しの
  連打も同じ）。同じカルテの別の対象も 1 つずつ通す。同時に送ると互いのプロンプトキャッシュを読めず、
  両方が書き込みの料金を払うため

### 使用量の記録と 1 日の上限

- 呼び出しごとに 1 行、`results/guide/usage.jsonl` に追記する。項目は、時刻・成否と失敗の種類・モデル・
  思考の深さ・キャッシュの保持時間・対象（セクション ID）・カルテの指紋・指示文の指紋・所要時間・
  4 つの計器（`input_tokens` / `cache_creation_input_tokens` / `cache_read_input_tokens` / `output_tokens`）・
  思考のトークン数・概算の費用。**カルテの中身、ガイドの文、API キーは残さない**（決まった項目だけを
  組み立てて書くので、紛れ込む経路が無い）
- 保存済みを返したとき（API を呼んでいないとき）は記録しない
- **費用は概算。** 単価の表（`backend/llm_pricing.json`。出典と取得日つき）から計算する。請求額そのもの
  ではないので、画面でも「概算」と出す。単価が変わったら、表を直すか、`results/guide/settings.json` の
  `pricing` で上書きする。表に無いモデルは、当て推量をせず、費用を出さない（トークン数だけ出す）
- **1 日の上限:** 既定は 20 回（2026-11-11 に利用者が決めた）。画面の設定で変えられる。概算の費用での
  上限（`daily_limit_usd`）も設定ファイルで指定できる。日付はこの Mac の時刻で数える。回数に数えるのは、
  応答が返ってきた呼び出しだけ（API キーの誤りや通信の失敗には費用がかからない）。上限に達していても、
  保存済みのガイドは見られる

### LLM に渡すカルテ（入力）

長い曲では、入力のほとんどをコードの一覧が占める（4 分の曲で、変更前は入力の約 9 割）。
言語化に使わない項目を外し、コードを表の形に詰めた。確信度のほかは、事実（値）を変えていない。

| 外した・変えた項目 | 理由 |
|---|---|
| 確信度（`confidence` `bpm_confidence` `suggested_confidence`） | 生値（0〜1）ではなく、画面と同じ 3 段階（確実 / たぶん / 自信なし）に直してから渡す。数値をしきい値と比べるのは機械的に決まる計算で、LLM にさせると言い間違えた（下の「モデルと思考の深さの比較」）。コードで直せば、画面の表示と必ず一致する。生値はカルテに残る |
| `grid.beat_times_sec` | 実測ビート列。数百個の数値で、言語化には使わない。数（`beat_count`）だけ残す |
| `source.filename` | 曲の事実ではない。指示文でも、ファイル名からの推測を禁じていた。送らなければ、利用者のファイル名が外に出ない |
| `chords[]` の `beat_index` `start_sec` `end_sec` | 小節・拍（`bar` `beat`）と長さ（`beat_count`）から決まる。ガイドは場所を小節で指す |
| `chords[]` の `root` `quality` | コード名（`symbol`）に含まれている |
| `chords[]` の並べ方 | 1 件ごとに項目名を繰り返さず、列の名前（`columns`）と行（`rows`）に分ける |

落としたあとも、コードの読み取り（小節・拍・長さ・度数・確信度の言い方）は、カルテの値と一致していた
（下の実測。変更前と変更後のガイドを、カルテと 1 件ずつ突き合わせて確かめた）。

入力の量は、送る前に確かめる。文字数が上限より小さければ、数えずに通す（トークン数は文字数を超えない。
実測で、文字数の約 6 割）。超えていそうなときだけ `messages.count_tokens` で数え（費用はかからない）、
上限を超えるなら:

- 対象が曲全体なら、Claude を呼ばずに「対象でセクションを選んで絞ってください」と知らせる
- 対象がセクションなら、コードの一覧をそのセクションの小節だけにして送る（`chords.only_section` に絞った旨を
  残す）。区切りより前が対象ごとに変わるので、対象をまたいだプロンプトキャッシュは効かなくなる

### 出力

- `max_tokens`（16,000）は **切れたときの歯止めで、節約の手段ではない**。モデルからは見えず、当たると応答が
  途中で切れて、費用だけかかって作り直しになる。下げて節約しようとしない
- 出力を短くするのは指示文で行う。「書く量について」として、overview は 2〜3 文、手順は曲全体で 5〜7 個
  （セクションに絞ったら 3〜5 個）、1 手順は 2〜4 文、コード進行は繰り返しの単位で示す、と書き、
  1 手順の長さの例を 1 つ添えた（例は書き方の目安で、値は「○○」にしてある。例の中の値を写させないため）
- 解析できた項目が少ないカルテでは、在る項目についてだけ書かせ、検出できなかった項目は注意書きに
  1 行ずつ挙げるだけにさせる。項目がほとんど無いカルテは、そもそも Claude を呼ばない

### プロンプトキャッシュが効く条件

キャッシュは、区切りより前のバイト列が完全に同じで、かつ次の指定が同じときだけ効く。
効かなくなってもエラーは出ない（請求が増えるだけ）ので、**リクエストの組み立てを変えたら、
コードを読んで判断せず `scripts/guide_probe.py cache --yes` で確かめる**（同じリクエストを 2 回送り、
2 回目に `cache_read_input_tokens` が立たなければ失敗で終わる。入力の使用量を受け取ったところで接続を
閉じるので、費用は 1 回 0.03 ドルほど）。

- **区切りより前に、時刻・乱数・呼び出しごとに変わる値を入れない。** 指示文は import 時に決まる定数。
  カルテは `to_canonical_json` を通してキー順・区切り文字・浮動小数点の桁を固定している
- **モデル・思考の深さ（effort）・thinking・出力の形（`output_config.format`）を、呼び出しごとに変えない。**
  モデルを変えると、キャッシュは必ず別物になる。思考の深さと thinking は、モデルによってはキャッシュを
  無効にする（Opus 5.5 では、実測で、思考の深さを medium から low に変えても指示文とカルテは
  キャッシュから読めた。ほかのモデルでは保証されない）。出力の形は区切りより前に入るので、変えれば切れる。
  いまは、モデルは `BUNRI_GUIDE_MODEL`（起動中は変わらない）、思考の深さは定数 `EFFORT`、出力の形は定数
  `GUIDE_SCHEMA`。**モデルを画面から切り替えられるようにした場合、切り替えた直後の 1 回はキャッシュが
  効かない**（保存済みのガイドも、モデルと思考の深さが鍵に入っているので使われない）
- **出力の形もキャッシュされる側に入っている。** 実測で、区切りまでの量は「指示文 + カルテ」の計数より
  約 1,670 トークン多かった（出力の形のぶん）
- **キャッシュできる最小の長さ。** Opus 5.5 / Sonnet 5.5 / Haiku 5.5 は 512 トークン。指示文だけで約 1,800
  トークン在るので、どんなに短いカルテでも下回らない。ただし `BUNRI_GUIDE_MODEL` で古いモデル
  （Opus 4.6 / 4.5、Haiku 4.5 は 4,096）を指定すると、短い曲では黙ってキャッシュされなくなる
- **同じカルテへの呼び出しを同時に送らない。** キャッシュは、最初の応答が始まるまで読めない

保持時間は既定の 5 分のまま（`CACHE_TTL`）。1 時間にすると書き込みが割高（入力の 2 倍。5 分は 1.25 倍）
なので、同じカルテへの次の呼び出しが 5 分〜1 時間のうちに来ることが多くないと、かえって高くつく。
ガイドを保存するようにしたので、キャッシュが効くのは「同じカルテに、対象を変えて問い合わせたとき」だけ。
実際の間隔は `uv run python scripts/guide_probe.py usage` で見られる（記録から、間隔の分布と、保持時間ごとの
入力の費用を出す）。記録が溜まってから決める。なお、キャッシュを温め直す方法（`max_tokens: 0` の送信）は、
出力の形を指定したリクエストでは使えない。

### 入れなかったもの

| 候補 | 入れなかった理由 |
|---|---|
| Batch API（半額） | 利用者が画面の前で待っているので使えない |
| ツール検索、コンテキスト編集、コンパクション、サブエージェント | 1 回の呼び出しで完結する機能なので、当てはまらない |
| `max_tokens` を下げる | 節約にならない（上の「出力」） |
| キャッシュの保持時間を 1 時間にする | 効果が呼び出しの間隔しだいで、まだ記録が無い。短い曲 1 回あたり、得でも損でも 0.01 ドル前後 |
| カルテの数値の桁を丸めて渡す | コードを表にしたあとは、減るのが数百トークン。解析の値そのものを変えることになる |
| モデルを設定画面から選べるようにする | 見送り。Sonnet 5.5 や Haiku 5.5 が、確信度を 3 段階で渡したあとの内容で使えるかを、まだ十分に確かめていない（1 回ずつ）。切り替えると、直後の 1 回はキャッシュが効かず、保存済みのガイドも使われない。いまは環境変数 `BUNRI_GUIDE_MODEL` で差し替えられる |

### 実測（2026-11-11）

合成した曲のカルテ 3 つで、実際に Claude を呼んで測った（`test/fixtures/charts/`）。「短い曲」は 33 秒・
コード 23 個、「長い曲」は 4 分・コード 196 個・セクション 12 個、「材料の少ない曲」は 6 秒のノイズ
（キーとコードが検出できない）。モデルは Opus 5.5、思考の深さは medium（このときの既定）。費用は単価の表からの概算で、
プロンプトキャッシュが効いていない 1 回目の値（どれも 1 回ずつの計測。思考に使われる量は回ごとに
数百〜数千トークン揺れるので、1 割程度の差は誤差のうち）。

| | 短い曲 | 長い曲 | 材料の少ない曲 |
|---|---|---|---|
| 変更前 | 入力 5,769 / 出力 3,885 トークン、39 秒、$0.107 | 入力 22,787 / 出力 5,147、46 秒、$0.217 | 入力 3,539 / 出力 2,555、27 秒、$0.069 |
| カルテを詰めて渡す | 入力 4,203 / 出力 4,236、$0.106 | 入力 8,938 / 出力 5,398、$0.153 | — |
| ＋ 書く量の目安（いまの実装） | 入力 4,757 / 出力 3,182、30 秒、$0.087 | 入力 9,492 / 出力 3,968、36 秒、$0.127 | 入力 4,168 / 出力 1,837、20 秒、$0.058 |
| 変更前との差 | −18% | −42% | −16% |
| 同じ条件で 2 回目に開く | $0（Claude を呼ばない） | $0 | $0 |

### 確信度を 3 段階で渡し、思考の深さを low にした（2026-11-11。上の比較を受けた変更）

上の比較を受けて、利用者の判断で 2 つ変えた。

1. **確信度を、コードの側で 3 段階に直してから渡す**（`prompt_chart`）。指示文からしきい値の説明を外し、
   「与えられた言い方のまま書く」とした。生値はカルテに残る
2. **思考の深さの既定を medium から low にする**（`EFFORT`）。1 を入れたうえで、low でも誤りが出ないことを
   確かめてから変えた

確かめ方: 製品のコードそのままで、Opus 5.5 / low のガイドを、短い曲と長い曲で 3 回ずつ、セクションに
絞ったものを 1 回ずつ、材料の少ない曲で 1 回作らせ、確信度の言い方をすべて、コードの説明を 1 件ずつ、
カルテと突き合わせた。比較のため medium も 1 回ずつ作らせた。

| | 短い曲 | 長い曲 |
|---|---|---|
| Opus 5.5 / low（いまの既定。3 回の平均） | 出力 2,607（うち思考 816）、25 秒、$0.075 | 出力 2,870（うち思考 736）、27 秒、$0.104 |
| Opus 5.5 / medium（1 回） | 出力 3,276（うち思考 1,314）、31 秒、$0.089 | 出力 3,605（うち思考 1,408）、34 秒、$0.119 |
| low の、medium との差 | −15% | −13% |
| いちばん最初（何も入れる前）との差 | −29%（$0.107 → $0.075） | −52%（$0.217 → $0.104） |

- **内容:** low の 9 回（曲全体 6、セクション 2、材料の少ない曲 1）で、確信度の言い間違いは 0、
  コードの読み取りの誤りは 0、落とした参照 0、カルテに無い語 0。medium の 2 回も同じ
- **費用の差は、上の比較で見込んだほど大きくなかった。** 上の比較では low の思考が 0 トークンだったが、
  今回は毎回 700〜800 トークン考えた（思考の量はモデルが回ごとに決める）。差は 3 割ではなく 1〜2 割
- セクションに絞ると、手順は 5 個、出力は 2,000〜2,250 トークン、$0.04〜0.05（キャッシュが効いた状態）
- 残る小さな癖: 検出できなかった項目（確信度 0）にも「自信なし」が付いて渡るので、「キーは検出できません
  でした（自信なし）」のような書き方になることがある。誤りではないので、そのままにしている
- **確かめたのは、合成した曲 3 つだけ。** モデルや指示文を変えたら、`scripts/guide_probe.py compare` で
  測り直してから決め直す。low で誤りが目立つ曲が見つかったら、`EFFORT` を medium に戻せばよい
  （戻すと保存済みのガイドは作り直しになる）

## 本物の Claude で確かめたこと（2026-11-11）

合成した曲（C → G → Am → F の繰り返し、120 BPM、32 秒）のカルテで、実際に Claude を呼んで確かめた。

- **出力の形が API に受け付けられ、最後まで通る。** 1 回あたり約 40 秒、出力は 4,000 トークン前後
  （費用を抑える変更の前の値。いまの値は上の「実測」）
- **参照はすべて実在の場所を指した**（落とした参照 0）。**カルテに無い音名・コード名も出なかった**
- **プロンプトキャッシュが効く。** 2 回目の問い合わせ（対象を 1 セクションに絞ったもの）で、
  指示文とカルテの約 5,300 トークンがキャッシュから読まれた
- **解析の誤りに気づく手がかりを出した。** 「コードの切り替わりが毎回 3 拍目に来ているので、
  1 拍目の位置が 2 拍ずれていないか確認を」という注意書きが出た（実際、この曲のグリッド検出は
  1 拍目を 1.0 秒の位置に置いていて、ずれていた）
- 画面からの通し（ファイルの読み込み → カルテ → ガイドの表示）も、ブラウザの自動操作で確認した
  （`web-ui/e2e/guide.spec.ts`。API を実際に呼ぶので、`BUNRI_E2E_LLM=1` を付けたときだけ走る）

最初の指示文で出た問題と、直したこと:

| 出た問題 | 直し方 |

## 確かめられていないこと

- **実際の楽曲での出来。** 確かめたのは合成した曲 1 つ。長い曲、テンポの揺れる曲、解析の確信度が
  低い曲で、どのくらい的確な手順が出るかは未確認
- 指示文の評価（複数の曲での比較、カルテに無い語をどの程度出すか）
- 画面でのハイライト。参照（セクション・小節）は文字で出しているだけで、タイムライン上の強調はまだ無い
- 左のパネルは幅が狭く、長い説明は読みにくい。表示の場所は見直す余地がある
