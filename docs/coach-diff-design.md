# 差分コーチ（第3層）— ノートの差分と、その言語化

第3層は「利用者の打ち込みと原曲の差分を指摘する」層で、製品の差別化の本命
（[song-chart-design.md](song-chart-design.md)）。実装したのは 2 つ。

1. **事実を出す部分**（ノートの差分）。LLM は使っていない。画面まで出来ている
2. **言葉にする部分**（どんな傾向の違いか、なぜ起きたと考えられるか、まず何を見直すか）。Claude を使う。
   画面まで出来ている（差分チェックの結果の下の「Claude に説明してもらう」）。下の「言語化（差分の説明）」

> **暫定の実装。** 第3層の設計はまだ詰めていない（学習履歴の置き場、お手本の見せ方など）。
> 「いま実装できるものを進めてよい」との指示で、設計の決定を待たずに作れる部分を先に作った。
> 言語化の決定も、実装者の判断で埋めたもの。本物の Claude では、まだ 1 回も確かめていない。

## 何が出来るか

お手本（原曲を採譜した時点のノート）と、いまの打ち込みを突き合わせ、次を返す。

- お手本のうち、高さと位置が合っていた割合
- 指摘の一覧。種類は 6 つ: 抜け / 高さの違い / オクターブ違い / 余分なノート / 位置のずれ / 長さの違い
  （画面での呼び名。ことばの決まりは [ui-terms.md](ui-terms.md)）
- 指摘が重い小節（まず見るとよい場所）
- 強さ（ベロシティ）の違い。**お手本が MIDI ファイルから読み込んだもののときだけ**。指摘の一覧とは別の欄に、
  まとまりで言える違いとして出す（下の「強さの違い」）

画面では左パネルの「学ぶ」タブの「差分」の段に「差分チェック」として出る。指摘は
「2 小節 3 拍目: E4 が抜けています」のように、決まった型の文にする（これも LLM ではない）。

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| お手本 | パート分離（採譜）で作ったパートのトラックが、採譜したノートを `referenceNotes` として持つ。打ち込み（`pianoNotes`）は**空のまま**渡す（2026-11 に変更。それまでは同じノートを打ち込みにも入れていて、差分が最初から 100% だった） | 比べる相手が最初から答えそのものだと、差分コーチが成り立たない（[song-chart-design.md](song-chart-design.md) の「ゴースト表示」）。採譜を自由に直したい人には「お手本をノートとして取り込む」を残す（確かめてから写す） |
| 比べる相手 | お手本を持つトラック自身、または別のトラック | 採譜を直した結果の確認にも、自分で一から打ち込んだものの確認にも使えるように |
| 突き合わせ | 同じ高さ → オクターブ違い → 2 半音以内の違い、の順に、位置の近いものから組にする | 軽い違い（位置・長さ）を、重い違い（抜け・余分）として数えないため |
| 位置の許容 | 16 分音符 2 個まで（ドラムは 1 個まで。下の「ドラムの差分」） | 人が打ち込むときの小さなずれを「別の音」にしないため。暫定の値 |
| 位置と長さの数 | 16 分音符単位のまま、小数を許す（三連符・32 分音符。下の「小数の位置と長さ」）。「位置のずれ」「長さの違い」として指摘するのは、差が 0.5 ステップ以上のときだけ | シャッフルや三連の曲で、お手本を 16 分に丸めたせいのずれを、利用者の違いとして指摘しないため。整数だけのノートの結果は変わらない |
| 正確さ | 高さと位置（許容内）が合っていたお手本の割合。長さの違いと小さな位置のずれは、合っている側に数える | まず「音が合っているか」を見せるため |

## 限界

- **お手本そのものが間違っていることがある。** お手本は自動採譜の結果で、原曲の正解ではない。
  採譜の誤りは、そのまま「抜け」「余分」として出る。画面では「お手本」と呼び、「正解」とは言っていない
- ドラムは、リズム（種類ごとの叩く位置）だけを比べる。長さと音の高さは比べない（下の「ドラムの差分」）。
  言語化（Claude の説明）は、ドラムでは出さない
- テンポ揺れは見ていない。お手本も打ち込みも、同じグリッド（16 分音符を 1 とするステップ。小数も可）に載っている前提。
  グリッドはカルテの平均のテンポの等間隔なので、テンポが揺れる曲では、曲の後ろほどカルテの実測の拍からずれる
- 採譜したお手本が載るグリッドは、16 分音符か、8 分の三連のどちらか 1 つ（曲全体で 1 つ。下の「採譜のグリッド」）。
  16 分の三連・32 分音符・5 連符の位置は、採譜では出ない（打ち込みと、MIDI から読み込んだお手本では扱える）

## 小数の位置と長さ（三連符・32 分音符。2026-11-18 に実装。値は暫定）

ノートの `step` と `length` は 16 分音符単位の整数だったので、三連符・32 分音符・スウィングを表せず、MIDI の読み込みも
採譜も 16 分に丸めていた。シャッフルや三連の曲では、お手本そのものが 16 分に丸まり（三連の 3 つ目 8/3 が 3 になる）、
差分は、グリッドのせいのずれを利用者の違いとして指摘していた。

### 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| 単位 | **16 分音符単位のまま、小数を許す**（1 = 16 分音符、0.5 = 32 分音符、4/3 = 8 分の三連、2/3 = 16 分の三連）。`steps_per_bar` `steps_per_beat` `timing_tolerance` は整数のまま | 単位を変えると、以前のプロジェクト・学習の記録・保存済みの説明が、全部ずれる。整数のノートは、そのまま正しい |
| 持ち方 | **1/60 ステップの倍数に丸める**（`backend/note_steps.py`。画面の `Math.round(x * 60) / 60` と同じ倍精度の値になる）。端数がちょうど 0.5 のときは大きいほうへ（Python の `round` は偶数へ丸めるので使わない） | 60 は 3・4・5 で割れるので、三連符・32 分・64 分・5 連符が、どれも刻みの上に乗る。丸めておけば、別の式で作った同じ位置（`4/3` と `1.3333`）が、同じ値になる |
| 整数になる値 | **整数（`int`）で返す**。JSON でも `4.0` ではなく `4` | 整数だけのノートから作る結果・保存・Claude に渡す事実が、1 文字も変わらない（保存済みの説明の鍵も変わらない） |
| 比べ方 | 刻みの数（1/60 ステップ単位の整数）に直してから比べる | 小数のまま引くと、`25/6 − 13/6` が 2.0000000000000004（許容 2 を超える）、`0.7 − 0.2` が 0.49999999999999994（下限 0.5 に届かない）のように、境目で結果が変わる |
| 受け付ける値 | `step` は 0 以上、`length` は 0 より大きい有限の数。bool・数でない値・NaN・無限・負の位置・0 以下の長さ・丸めると 0 になる長さ（1/120 ステップ未満）は、これまでどおり形式の誤り（400） | 形式の誤りの扱いは変えない |
| 許容（`timing_tolerance`） | **意味は変えない**（ふつう 2、ドラム 1。その幅までなら同じ音として組にする） | 一致率の数え方を変えない（学習の記録の「前回より」が比べられなくなる） |
| 「位置のずれ」の指摘の下限 | **0.5 ステップ以上**のときだけ指摘する（`MIN_TIMING_ISSUE_STEPS`） | 下の「指摘の下限の根拠」 |
| 「長さの違い」の指摘の下限 | **0.5 ステップ以上**（`MIN_LENGTH_ISSUE_STEPS`）。ドラムは、これまでどおり長さを比べない | 位置と同じ考え。お手本の長さ 4/3（8 分の三連）に、16 分音符 1 個（差 1/3）は指摘せず、8 分音符（差 2/3）は指摘する |
| `exact`（位置も長さも一致） | 下限より小さい差は、一致に数える。`exact` + （位置か長さの指摘が付いた組）= 同じ高さで組になった数、のまま | 指摘が 1 つも付かない組を「一致」と呼ぶ、という意味を変えない |
| 小節と拍（`bar` `beat`） | **いつも整数**。そのノートが始まる小節と拍（拍の途中で始まるノートは、その拍に数える。三連の 3 つ目は、その拍） | 画面の「2 小節 3 拍目」の文、指摘からの移動、`bar_stats`、説明の参照が、そのまま使える。小数の拍を、どこにも出さない |
| `offset_steps` `length_diff` | 実際の差（1/60 ステップの倍数。整数になる値は整数）。下限より小さい差も、そのまま載る（たとえば、位置のずれの指摘に `length_diff: 0.3333333333333333`） | 画面は、種類（`kind`）で出し分ける。差の値を、下限で切り捨てて嘘にしない |
| 言語化に渡す事実 | 整数のノートでは、**バイト単位で同じ**（指示文・出力の形・版も変えていない）。小数のノートのときだけ、指摘の表の `offset_steps` `length_diff` が小数 2 桁になる（`-0.67`。`mean_offset_steps` と同じ桁）。小節・拍・小節の数は整数のまま | `0.6666666666666666` を渡しても、読みにくいだけで情報が増えない。指示文には「単位はステップで、1 拍が `grid.steps_per_beat` 個」と書いてあり、小数のステップも、その読み方のまま読める |

### 指摘の下限の根拠

これまでは整数どうしだったので、ずれが 0 でなければ（= 1 ステップ以上）指摘していた。小数になると、そのままでは
1/60 ステップの違いまで指摘になる。

- **16 分と三連の隣どうしは、指摘しない。** 16 分の位置（1・3）と、いちばん近い三連の位置（4/3・8/3）の差は 1/3 ステップ。
  16 分で採譜したお手本（これまでのプロジェクト、三連と見分けられなかった曲）に、三連の刻みで打ち込んだとき、
  また逆のときに、全部のノートが「位置のずれ」になるのを避ける。120 BPM で 1/3 ステップは 42 ミリ秒
- **8 分の裏と三連の裏の違いは、指摘する。** 8 分の裏（2）と三連の 3 つ目（8/3）の差は 2/3 ステップ。これは、
  ふつうの 8 分とシャッフルの違いそのもので、聴いて分かる（120 BPM で 83 ミリ秒）
- **境目を 0.5 にした理由。** 1/3 と 2/3 の真ん中。32 分音符 1 個ぶん（0.5）のずれは、指摘になる（32 分で打ち込める刻みで
  1 つ隣に置いたら、ずれ）。16 分の三連の隣どうし（2/3）も指摘になる
- **整数どうしの結果は、変わらない。** 整数の差は 0 か 1 以上で、0.5 をまたがない。実装のときに、小数を許す前のコードと、
  乱数で作った整数のノート 4,000 組（ふつうの比べ方・ドラム・強さ。拍子と許容も変える）で結果を比べ、差分 12,000 件と、
  言語化に渡す事実 8,000 件が、どれも同じ文字列になることを確かめた（既存のテストも、1 つも書き換えていない）
- **測っていないこと。** 人がスウィングの付いた曲を打ち込んだときの、ずれの分布。0.5 は、グリッドの位置どうしの差から
  決めた値で、実際の打ち込みでは確かめていない

### 保存

`.bunri` の `project_notes` の `step` `length` は、列の宣言を INTEGER のままにしてある。SQLite は、整数になる値を整数で、
整数に直せない実数を実数のまま持つので、列を足さずに往復する（[song-chart-design.md](song-chart-design.md)「プロジェクトの保存」）。
以前の形式（`projects/*.json`）を開くときも、小数を切り捨てない。

### 確かめられていないこと・扱っていないこと

- **小数のノートを、小数を許す前の版の bunri で開いたとき。** 形式の版は上げていないので開けるが、その版の画面と差分は
  整数を前提にしている（差分の API は、小数のノートを形式の誤りとして断る）
- `/api/synth/sequence`（ツールのステップシーケンサー）と `/api/analyze`（単音の解析）は、16 分のまま（小数の位置を
  渡すと、シーケンサーは切り捨てる）
- 強さの違い（`velocity_diff`）のまとまりの決まりは、変えていない（小節ごとに数えるので、小数の位置でもそのまま）

## 強さの違い（2026-11 に実装。どれも暫定）

**利用者が決めたこと（2026-11-13）: お手本が MIDI ファイルから読み込んだもののときだけ、強さの違いを差分に出す。
音源から採譜したお手本では、強さに一切触れない。**

採譜（basic-pitch）のお手本の強さは、音の大きさ（amplitude）× 127 で、きれいな合成音でも 24〜120 が 76〜97 に潰れる
（72 以上は区別できない）。当てになるのは、MIDI ファイルに書かれていた強さだけ。

### 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| お手本の出どころ | 画面が、差分の API に `reference_source` で渡す。`"midi"` のときだけ強さを比べる。無い・`"transcription"`・そのほかの値・文字列でない値は、どれも「比べない」 | 出どころを知っているのは画面だけ（MIDI ファイルからお手本として読み込んだトラックは `role: 'part'` で `part` が `MIDI_PART`。`lib/learn.ts` の `referenceSourceOf`）。新しい区別は足さず、既に在るものを使う。以前の形式から開いた、出どころの分からないお手本は、採譜と同じ扱いになる（比べないほうへ倒す） |
| 一致率 | **変えない。** 強さは `summary` にも `bars`（指摘の一覧）にも `worst_bars` にも入れず、結果の別の項目 `velocity` に出す | 学習の記録の「前回より」が、過去の値と比べられなくなるため。指摘の ID（`i1` `i2` …。説明の参照と保存済みの説明が使う）も変わらない |
| 比べる相手 | 位置と高さが合った組（一致率に数えた組）だけ | 抜け・余分・高さの違いは、まずそちらを直す。別の音どうしの強さを比べても意味が無い |
| 強さを持たないノート | 96 として比べる（`DEFAULT_VELOCITY`。画面と同じ値） | マウスで置いたノートは強さを持たず、96 で鳴る。聞こえる強さと比べる |
| 許す幅 | **16**（差が 16 以内なら同じ強さ。17 から違い） | 下の「許す幅の根拠」 |
| 出す形 | 1 ノートごとの差は並べず、まとまりで言える 4 つの形にする（下の表）。数（弱い・強いノートの数）と、どのノートか（`notes`）は、別に持つ | マウスで置いたノートは全部 96 なので、強弱の付いたお手本と比べると、ほとんどのノートが「違う」になる。1 ノートずつ並べると、位置や高さの指摘が埋もれる |
| まとまりに要る数 | 3 ノートから（アクセントは 2 個から） | 1〜2 ノートだけの違いは、弾きむらと区別できない。アクセントは、もともと数が少ない |
| 学習の記録 | 強さは入れない | 記録の形（一致率と 6 種類の件数）を変えない。強さの「前回より」は、要ると分かってから |
| Claude を呼ぶ条件 | 変えない（位置・高さ・長さの違いが 3 か所より少なければ呼ばない）。強さだけが違うときは、決まった文で強さの欄へ案内する（`velocity_only`） | まとまりは多くても数個で、強さの欄を読めば足りる |

### まとまりの形

事実を出すのは `coach_diff.velocity_diff`（LLM 不使用）。差（打ち込み − お手本）が許す幅を超えたノートを「弱い」「強い」と数え、次の形にまとめる。

| `kind` | 画面の文 | 条件 | 出さないとき |
|---|---|---|---|
| `overall` | 全体に弱い / 全体に強い | 比べたノートの 4 分の 3 以上が、同じ向きに違う | — |
| `flat` | 強弱が付いていません | 打ち込みの強さの幅（最大 − 最小）が 16 以内で、お手本の幅は 32 を超え、違うノートが 1 つは在る | — |
| `section` | 3〜4 小節が弱い / 強い | 過半数のノートが同じ向きに違う小節の、ひと続き（違うノートが 3 つ以上） | `flat` のとき（原因は「強弱が無い」で、範囲ごとに言うと言い直しになる）。`overall` と同じ向きのもの |
| `accent` | アクセントが付いていません | お手本で周りより強いノート（お手本の強さの中央値より 16 を超えて強い）の半分以上、かつ 2 個以上が、お手本より弱い | `flat` のとき、全体に弱いとき、どれも弱い範囲（`section`）の中に在るとき |

「全体に」を中央値ではなく 4 分の 3 にしたのは、半分だけ弱いときに「全体に弱い」と言うと、どこを直すかが分からなくなるため
（そのときは小節の範囲で言う）。まとまりにならなかった違い（1〜2 ノート）は、数だけを出す。

### 許す幅の根拠

- **強弱記号 1 段階ぶん。** MIDI の強さを強弱記号に当てるときは、16 刻みに置くのが広く使われている
  （pp 32、p 48、mp 64、mf 80、f 96、ff 112）。16 以内の差は、同じ強弱記号の中の違い。
  この対応は実装者の記憶によるもので、出典は確かめていない
- **このアプリでの聞こえ方。** ノートの音量は強さに比例する（`noteLevel`。96 が基準）。96 のノートに対して 112 は +1.3 dB、
  80 は −1.6 dB で、音量の違いが聞き分けられるかどうかの境目（1 dB 前後と言われる）に近い。これより細かい差を指摘しても、聞いて確かめられない
- **画面の操作の刻み。** 「強さ」の欄の −/＋ は 10 ずつ。1 回ぶんのずれ（10）は指摘せず、2 回ぶん（20）からは指摘する
- **測っていないこと。** 人が MIDI 鍵盤で「同じ強さ」のつもりで弾いたときのばらつき。16 より大きければ、鍵盤で弾いた打ち込みに
  余計な指摘が出る。本物の鍵盤と、実際の MIDI ファイルでは、まだ確かめていない

### 言語化

- 強さを比べたときだけ、事実に `velocity` を足す（まとまり・数・強さの範囲・違うノートの在る小節）。1 ノートごとの一覧は渡さない。
  まとまりは 12 個まで（`findings_total` が全部の数）
- そのときだけ、指示文の後ろに強さの読み方（`VELOCITY_PROMPT`）を、2 つ目の system として足す（キャッシュの区切りの後ろ）。
  「強さについて書いてよいのは、まとまりに在ることだけ」「1 ノートごとの数を並べない」「強さの数を自分で決めて勧めない」
  「『強さ』と書き、『ベロシティ』『音量』とは書かない」「このお手本は MIDI ファイルから読み込んだもの」
- **採譜したお手本では、事実も指示文も、強さを比べる前の版とバイト単位で同じ。** 強さという言葉そのものを Claude に渡さない
  （「一切触れない」を、形の上で守る）。保存の鍵も変わらないので、それまでの保存済みの説明もそのまま使える
- 強さの違うノートが在る小節は、説明の点が指してよい小節に足す（位置・高さの指摘が無い小節でも、落とさない）
- 高さ・位置・長さが全部合っていて、強さだけが違うとき: Claude を呼ばず、「次は『強さの違い』の欄を見て…」と案内する
  （`reason` が `velocity_only`）。強さも合っているとき（MIDI のお手本）は、「お手本は自動採譜の結果なので…」とは言わない

### 画面

- 差分チェック（左パネル）と練習画面の右の一覧に、「強さの違い」の欄を出す（`components/VelocityFindings.tsx`）。
  1 行のまとめ（「MIDI ファイルから読み込んだお手本なので、強さも比べています。合った 24 ノートの強さを比べました（お手本より弱い 6 / 強い 2）」）と、
  まとまりの一覧（8 個まで）。強さを持たないノートが在れば「マウスで置いたノートは強さを持たないので、96 として比べています」
- まとまりを押すと、当たるノートを選んで光らせ、その場所へ移る。選ばれるので、そのままピアノロールの上の「強さ」の欄で変えられる
- 強さが合っていれば、合っている旨を 1 行だけ出す。位置と高さの合ったノートが 1 つも無ければ、欄を出さない
- **採譜したお手本では、欄そのものを出さない**（「比べられません」とも出さない）。MIDI のお手本のときだけ、「お手本と比べる」の
  ボタンの説明（ツールチップ）に「強さも比べます」と添える
- 強さだけが違うときは「お手本どおりです」と言い切らず、「高さ・位置・長さは、お手本どおりです」と出す
- ノートの色（練習画面の印）は変えない。強さの違いは、押したときに光るだけ（色を増やすと、位置・高さの印が読みにくくなる）
- 練習画面で強さを変えると、ノートを変えたときと同じく「もう一度比べてください」になる

### 確かめられていないこと・扱っていないこと

- 本物の Claude で、強さの読み方の指示文がどう効くか（まとまりだけを言うか、数を並べないか）。偽のクライアントでしか動かしていない
- 実際の MIDI ファイル（市販・配布のもの）と、本物の MIDI 鍵盤で弾いた打ち込みでの出方。許す幅と「4 分の 3」「3 ノートから」は、
  合成したノートでしか確かめていない
- お手本で弱く弾くノート（ゴーストノート）が強すぎる、という指摘は出していない（弱い範囲・強い範囲としては出る）
- だんだん強く・弱く（クレッシェンド）のような、形の違いは見ていない
- 練習画面の区間の端で、相手のいないノートは比べない（位置・高さの差分と同じ）

## ドラムの差分（2026-11-18 に実装。値はどれも暫定）

ドラムは、それまで差分の対象外だった。採譜は、ドラムの音声 1 本のオンセットを 1 つずつ、音の明るさ（スペクトル重心）で
キック / スネア / ハイハットに振り分けるだけで（同時に鳴った音を 1 つにしか数えられない）、結果は打ち込みのノートとして
直接置いていた。初心者が最初に手を付けやすいパートなのに、「差分で直す」が使えなかった。

### 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| 形 | ドラムも、ほかのパートと同じ。パート分離で作るドラムのトラックは、打音をお手本（`referenceNotes`）として持ち、打ち込みは空。「このパートを練習する」で練習のトラックを作り、練習画面で打ち込んで比べる | 比べる相手が最初から答えそのものだと、差分が成り立たない（上の「決めたこと」の「お手本」と同じ）。練習の地図・学習の記録・区間ループも、そのまま使える |
| 種類 → 高さ | キック C2（36）・スネア D2（38）・ハイハットとシンバル F#2（42）・タム A2（45）。`web-ui/src/lib/drums.ts` の `DRUM_ROWS` 1 か所 | GM（General MIDI）のドラムの並び。MIDI に書き出して、ほかの DAW のドラム音源で鳴らしても、同じ種類になる。キック・スネア・ハイハットは、それまでの置き方のまま |
| ハイハットとシンバル | 同じ行（F#2） | 種類ごとに分けるモデルが、この 2 つを 1 つの音声（`cymbals`）にまとめて出す。分けない採譜の `hihat` も同じ行に置く |
| タム | 1 つの行（A2） | 分けるモデルが、タムを 1 つの音声にまとめて出す（高い・低いの区別は取れない） |
| 比べ方 | `coach_diff.diff_notes(mode="drums")`。同じ高さ（= 同じ種類）どうしだけを組にし、位置のずれが許容以内なら合っている。**長さは比べない**。高さの違い・オクターブ違いは出さない | ドラムのノートの高さは音の高さではなく、種類。「近い高さ」に意味が無い（C2 と D2 は、2 半音違いの「高さの違い」ではなく、キックとスネア）。打音に長さは無い（マウスで置いたノートの長さが、お手本の 1 ステップと違っても、指摘にしない） |
| 種類を間違えた打音 | お手本の「抜け」と、打ち込みの「余分なノート」として出る | 「スネアの位置にキックを置いた」は、スネアが抜けていて、キックが余分 |
| 出る種類 | 抜け（`missing`）/ 余分なノート（`extra`）/ 位置のずれ（`timing`）の 3 つ。`pitch` `octave` `length` は、いつも 0 件 | 結果の形（`summary` の欄）は、ふつうの比べ方と同じにしてある |
| 位置の許容 | **16 分音符 1 個**（ふつうの比べ方は 2 個のまま）。`timing_tolerance` を渡さなければ、比べ方で決まる（`coach_diff.TIMING_TOLERANCE`） | 下の「許容の根拠」 |
| 一致率・`bar_stats`・結果の形 | ふつうの比べ方と同じ（同じ種類で、位置が許容以内で組になったお手本の割合。小節ごとの合計は、全体の数と一致する） | 学習の記録・練習の地図・練習画面の「一致」が、そのまま使える |
| 比べ方の指定 | 画面が、お手本のトラックから決めて API に `mode` で渡す（`lib/drums.ts` の `diffModeOf`。お手本がドラムのパートなら `drums`）。差分チェックの段・練習画面・アシスタントの `check_diff` が、どれもこの 1 つの関数で決める | どこから比べても同じ結果にする。許容は画面からは送らない（API の側が、比べ方から決める） |
| 言語化（Claude の説明） | **ドラムでは出さない。** 差分チェックの段は、説明のボタンの代わりに決まった文（「ドラムの差分は、Claude の説明には対応していません…」）を出し、保存済みの説明も探さない（`/api/coach/explain` `/api/coach/explain/saved` を呼ばない） | 言語化の指示文と事実の組み立て（半音の差、コードの何度か、キーの音階に在るか）は、高さの違いを前提にしている。ドラムに合わせて変えると、版を上げて本物の Claude で確かめる必要がある。`coach_explain.py`・指示文・版は変えていない |
| 指摘の文 | 音名の代わりに、種類の名前で書く（「1 小節 2 拍目: スネア が抜けています」。`issueText(issue, 'drums')`）。ドラムの行でない高さに置いたノートは、音名のまま | 「D2 が抜けています」では、どの太鼓か分からない |
| 以前のプロジェクト | お手本を持たないドラムのトラック（採譜したリズムが、打ち込みに直接置いてある）は、そのまま開けて鳴らせる。「このパートを練習する」は押せない状態で出し、理由（分け直すと使える）を付ける（`lib/drums.ts` の `isLegacyDrumPart`） | 開いたときに勝手に作り替えない（打ち込みを直していたかもしれない）。分け直せば、新しい形になる |

### 許容の根拠

- **8 分音符ぶんの違いは、ずれではなく、別のリズム。** ドラムは、同じ種類の打音が 8 分・16 分の間隔で並び、表に打つか裏に打つかが
  リズムそのものになる。許容が 2 個（8 分音符 1 個ぶん）だと、裏に打つべき打音を表に打っても「位置のずれ」として合っている側に
  数えてしまい、16 分で刻むハイハットでは、打っていない打音の代わりに、2 つ隣の余った打音が組になりうる
  （「抜け」と「余分」が「位置のずれ」に化け、一致率が上がる）。1 個なら、組になれるのは隣だけ。近いものから組にするので、
  ぴったりの相手が居ればそちらが先に組になる（テスト: 16 分で 16 個のお手本に、裏の 8 個だけを打つと、ぴったり 8・抜け 8 になり、
  位置のずれも余分も出ない。スネアを 2 個ずらすと、ドラムでは抜け + 余分、ふつうの比べ方では位置のずれ）
- **1 個は残す。** 採譜はオンセットをステップに丸めているので、お手本そのものが 1 ステップずれていることが在る。
  0 個にすると、その分が全部「抜け + 余分」になる
- **測っていないこと。** 実曲の採譜の位置の誤差の分布と、人が打ち込んだときのずれ。合成したノートでしか確かめていない

### 採譜（お手本の作り方）

`backend/decompose.py`。`/api/decompose` に `split_drums=true` を付けると、ドラムを種類ごとに分けてから採譜する。

1. 6 パートに分けたあと、ドラムのステムを、追加のモデル（drumsep。`stem_models.py`、`separate.separate_drums`）で
   キック / スネア / タム / シンバルの 4 本に分ける（ツールの画面の「ドラムをさらに分ける」と同じ処理）
2. 4 本それぞれでオンセットを検出し、その種類の打音にする（`transcribe_drum_stems`）。同時に鳴ったキックとシンバルが、両方出る
3. 打音を、ステップに丸めてイベントにする（`drum_hits_to_events`。秒 → ステップは、ここ 1 か所の `seconds_to_step`）。
   丸める先は、16 分音符か、8 分の三連（曲全体で 1 つ。下の「採譜のグリッド（16 分か、三連か）」）

分けた 4 本の音声は、採譜の材料にだけ使い、パート（トラック）にはしない。結果の `drum_source` が `"stems"`。
種類は `kick` `snare` `toms` `cymbals`。

**落とす経路。** `split_drums` を付けない、追加のモデルを用意できない（オフラインなど）、分けた音声がどれも無音・打音を
取れなかった、のどれかのときは、それまでのスペクトル重心の振り分け（`transcribe_drums`）で採譜する。`drum_source` が
`"spectral"`、種類は `kick` `snare` `hihat`。頼まれたのに落としたときは、理由を `drum_fallback` に入れる（失敗にはしない。
`deep_separate` は、モデルを用意できなければ分離を始める前に止まるので、やり直しても、済んだ分離を捨てることにはならない）。
どちらの経路でも、画面はドラムをお手本にする。

**モデルのダウンロードは、利用者が選んだときだけ**（約 160 MB）。「パートに分ける」の「ドラムを種類ごとに分ける」は、
追加のモデルが手元に在るときだけ最初から選ばれている。無いときは選ばれておらず、選ぶとダウンロードが入る旨を出す
（`/api/models/drumsep/status` で聞く）。アシスタントから始めたパート分離は、モデルが手元に在るときだけ分ける。

誤検出を抑える仕組みと値（どれも `decompose.py` の定数。合成した音源で確かめた）:

| 仕組み | 値 | 何を防ぐか・根拠 | 取りこぼすもの |
|---|---|---|---|
| 同じ種類の打音の、最小の間隔 | 0.05 秒（`DRUM_MIN_INTERVAL_SEC`）。近い 2 つは 1 つにまとめ、強いほうを残す | 残響や、1 回の打音の中の 2 つ目の山（フラム、スネアの響き線）を、2 度打ちに数えない。150 BPM の 32 分音符（0.05 秒）までは、別の打音として残る | 0.05 秒より速い連打（ロール）は、間引かれる |
| 同じ種類・同じステップの打音 | 1 つにする（強いほうを残す） | 16 分音符より細かい連打が、同じステップに 2 つ並ぶのを防ぐ | 16 分より細かい打音（グリッドを細かくすると、残せる） |
| その種類の中での、小さすぎる打音 | その種類のふつうの大きさ（打音の大きさの 90 パーセンタイル）の 0.2 倍（約 −14 dB）より小さい打音を捨てる（`DRUM_BLEED_RATIO`） | 本物の打音が在るステムに、薄く残った別の種類（キックのステムに残ったスネア）。分離の漏れ込みは、本物の打音よりずっと小さい | ふつうの打音より 14 dB 以上弱いゴーストノート |
| 絶対の下限 | 振幅 0.01（約 −40 dBFS）より小さい打音を捨てる（`DRUM_MIN_LEVEL`） | 分離の残りかすだけのステム | とても小さく録音された曲の打音 |
| ほかの種類の「影」 | その種類の打音の 8 割以上が、ほかの 1 つの種類の打音と同時（0.03 秒以内）で、ふつうの大きさがその種類の 0.25 倍（約 −12 dB）より小さいとき、同時の打音を捨てる（`DRUM_SHADOW_*`）。キック・スネア・タムだけ | 本物の打音が無いステムに残った別の種類（曲にタムが無いのに、タムのステムにスネアが薄く残る）。上の 2 つでは防げない（そのステムの「ふつうの大きさ」が、漏れ込みそのものになる） | いつもほかの種類と同時に、ずっと小さく鳴る太鼓（たとえば、スネアに毎回重ねた小さなタム） |
| シンバル（ハイハット）は「影」の判定をしない | — | ハイハットは、キックやスネアと同時に、ずっと小さく鳴るのがふつう（4 分で刻むハイハットは、全部がキックかスネアと同時） | シンバルのステムに残った、ほかの種類の漏れ込み（絶対の下限と、小さすぎる打音の判定だけが効く） |
| 音声の頭の打音 | 音声の頭に 0.1 秒の無音を足してから、オンセットを調べる | オンセット検出は「前より大きくなった所」を探すので、音声のいちばん頭で鳴った打音が見つからない | — |

強さ（ベロシティ）は、その種類のふつうの打音を 96 とした相対の値（種類どうしの音量の比は入らない）。採譜したお手本なので、
差分では強さを比べない（上の「強さの違い」）。

### 採譜の限界・確かめられていないこと

- **実曲では、1 回も確かめていない。** 追加のモデルを実際に動かしての確認はしておらず（実装のときは、モデルをダウンロードして
  いない）、分けた音声の質・漏れ込みの大きさ・上の値が実曲に合うかは、分からない。合成した音源（キック・スネア・ハイハット・
  タムを決まった位置に置いた WAV。漏れ込みは、別の種類を小さく混ぜて作った）でしか確かめていない
- ハイハットの開閉、シンバルの種類（クラッシュ・ライド）、タムの高低、リムショットやゴーストノートは、区別しない
- 位置は、オンセット検出のフレーム（約 23 ミリ秒）刻み。速いテンポ・細かいグリッドでは、ステップが 1 つずれうる
- 落とした経路（スペクトル重心）のお手本は、同時に鳴った種類が 1 つにまとまっている。そのお手本と比べると、
  正しく打った打音が「余分なノート」に出る（画面は、分けずに採譜した旨を出す）
- 「その他」を分け直したパーカッション成分（`other_drums`）は、いつも落とした経路で採譜する

### 画面

- **鍵盤の列**: ドラムのトラック（ドラムのパートと、その練習のトラック。`lib/drums.ts` の `isDrumTrack`）をピアノロールで開くと、
  ドラムの行に、音名の代わりに種類の名前（キック / スネア / ハイハット・シンバル / タム）が出て、その行が見える位置へ
  スクロールする。名前が入るよう、列が広がる（`PianoRollEngine._syncDrumMode` `_labelKeys`）。キーの音・コードの音は出さない
- **刻み**: ドラムのトラックの刻みは、既定が 16 分（置くノートの長さも 1 ステップ）。ふつうのトラックの既定は 1 拍で、
  そのままでは 8 分・16 分のハイハットをマウスで置けないため。刻みは、ピアノロールの見出しで選べる（4 分 / 8 分 / 16 分 / 32 分 /
  8 分の三連 / 16 分の三連。ドラムのトラックの刻みとして、ふつうのトラックとは別に覚える。`lib/snap.ts`・`components/SnapBar.tsx`）。
  三連のグリッドで採譜したドラムのお手本も、長さは 1 ステップのまま（三連の間隔は 4/3 ステップなので、重ならない。長さは比べない）
- **三連の曲の練習**（ドラムに限らない）: お手本が三連のグリッドに載っているパートの練習を始めると、刻みを「8 分の三連」に合わせて、
  その旨をステータスバーに出す（`lib/learn.ts` の `alignSnapToReference`）。三連かどうかは、お手本のノートの位置から見分ける
  （`lib/snap.ts` の `gridFeelOf`。三連の位置にしか無いノートが 2 つ以上で、ストレートの裏の 3 倍以上、どちらでもない位置より多い。
  API の `grid_feel` はトラックに覚えない。開き直したプロジェクトや、MIDI から読み込んだお手本でも同じに働くように）。
  合わせるのはパートごとに 1 回で、利用者が変えたら従う。利用者が覚えさせた刻みは書き換えない
- **指摘の文の幅の言い方**（画面の側。`lib/coach.ts` の `issueText` → `lib/snap.ts` の `spanLabel`）: 1 拍の倍数は「1 拍ぶん」、
  16 分音符の倍数は「16 分音符 2 個ぶん」（ここまでは、これまでと同じ）、三連は「8 分の三連符 1 個ぶん」「16 分の三連符 1 個ぶん」、
  32 分は「32 分音符 1 個ぶん」。小数のまま「16 分音符 0.67 個ぶん」とは出さない。どの音符の倍数でもない幅（人が弾いた MIDI の
  お手本）だけ「16 分音符でおよそ 0.8 個ぶん」。指摘とノートの対応（色分け・一覧から光らせる）は、高さと、位置・長さの
  刻みの数（1/60 ステップの整数）で取る（`shapeOf`）。範囲に入るか・小節の判定も、刻みの数で比べる（`lib/grid.ts` の `toTicks`）
- **音**: ドラムのトラックのノートは、種類ごとの簡単な合成音で鳴る（`lib/drum-sound.ts` の `playDrum`。キック: 下がるサイン波、
  スネア: ノイズ + 短い音、ハイハット・シンバル: 高域のノイズ、タム: 下がるサイン波）。再生・区間ループ・書き出し・鍵盤の試し聴き・
  MIDI 入力のモニターが、同じ関数を使う。ドラムの行でない高さのノートは、これまでどおり三角波。強さは音量に反映する。
  打った瞬間の音なので、再生位置がノートの頭を過ぎていたら鳴らさない。打ち込み用の音源を Rust のエンジンに移す
  （[instrument-engine-design.md](instrument-engine-design.md)）までのつなぎ
- **差分チェック・練習画面**: 比べ方の説明（「ドラムは、種類ごとの叩く位置を比べています。長さは比べません…」）を、決まった文として出す
- **アシスタント**: `check_diff` はドラムでも通る（同じ `diffModeOf`）。結果に、比べ方の説明（`comparison`）と、ノートごとの
  種類の名前（`drum`）を添える。台帳と指示文は変えていない（「ドラムは比べられない」の記述は、もとから無かった）

## 採譜のグリッド（16 分か、三連か。2026-11-18 に実装。値はどれも暫定）

採譜（`backend/decompose.py`）は、検出した音の始まりと長さを、16 分音符に丸めていた。シャッフルや三連の曲では、
三連の 3 つ目（拍の頭から 8/3 ステップ）が 3 に、2 つ目（4/3）が 1 に丸まり、お手本そのものが原曲からずれる。
そこで、**曲がはっきり三連のときだけ**、三連のグリッド（1 拍を 3 つに割る = 8 分の三連。4/3 ステップおき）に丸める。
信号処理の事実だけで決める（LLM は使わない）。

### 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| 見分けるグリッド | 16 分音符（`straight`）か、8 分の三連（`triplet`。1 拍 3 つ）の 2 つ。**16 分の三連（1 拍 6 つ）は見分けない** | 1 拍 6 つのグリッドは、8 分の裏（2 ステップ = 6 つのうちの 4 つ目）を含む。ふつうの 8 分の曲が、ずれ無しで合ってしまい、ずれの大きさでは 16 分と区別できない（取り違えの元になる）。16 分の三連が続く曲は、16 分のまま |
| 決める単位 | **曲全体で 1 つ**。全部のパートの音の始まりから決め、全部のパートを同じグリッドに丸める | パートごとに決めると、同じ曲の中でグリッドが食い違う（下の「曲全体か、パートごとか」）。合わせて打ち込むときに混乱する |
| 迷うとき | **16 分**（これまでと同じ丸め方） | ふつうの曲を三連と取り違えると、8 分の裏（2）が三連の位置（4/3 か 8/3）へ動き、お手本が大きくずれる。三連の曲を 16 分のままにしても、これまでと同じ結果になるだけ |
| 判定に要る音の数 | 曲全体で 32 個から（`GRID_FEEL_MIN_ONSETS`）。少なければ 16 分のまま | 三連で 1 小節を埋めると 12 個。2 小節ほどの偶然で決めない。ふつうの長さの曲は、数百個以上在る |
| 丸め方 | 位置も長さも、同じグリッドに丸める（`seconds_to_step` `seconds_to_length`）。三連のとき、位置は 4/3 の倍数（拍の頭は整数、ほかは小数）、長さは 4/3 以上の 4/3 の倍数。16 分のとき、これまでどおり整数（結果は 1 文字も変わらない） | 長さだけ 16 分のままだと、三連で並ぶノートが重なる・すき間が空く |
| 結果 | `/api/decompose` の結果に `grid_feel`（`"straight"` か `"triplet"`）。各ステムにも同じ値を載せる | 画面が、練習の刻みを合わせるのに使う。ステムにも載せるのは、画面がパートごとにトラックを作るときに、そのまま持たせられるように |
| ジョブの約束 | 変えていない（ステージの並び・進み具合・キャンセルの効く場所・書きかけの削除。[jobs.md](jobs.md)）。丸めるのは、全部のパートの採譜が済んだあとの一瞬 | 見分けには、全部のパートの音の始まりが要る。パートごとの採譜は、丸める前の音（秒）までを取っておく |
| 見分けない経路 | `/api/analyze`（単音の解析）と、`transcribe_polyphonic` `transcribe_drums` `transcribe_drum_stems` を単体で呼んだとき（渡さなければ 16 分） | 1 パートだけでは、曲全体のグリッドを決められない |
| グリッド推定（テンポと 1 拍目） | 変えていない（`structure.py`） | 見分けは、決まったテンポと 1 拍目の位置の上で行う |

### 見分け方（`decompose.detect_grid_feel`）

1. パートごとに、同時に鳴った音（0.03 秒以内。和音、キックとハイハット）を 1 つにまとめ、音の始まりをステップ（小数）に直す。
   1 小節目より前（弱起）の音は数えない
2. 4 拍（16 ステップ）の窓ごと・パートごとに、音の位置を、16 分のグリッド（1 ステップおき）と三連のグリッド
   （4/3 ステップおき）のそれぞれへ当てはめる。**グリッド全体を前後にずらしてよい**（窓・パートごとに 1 つ。間隔を 60 に
   割った候補から、いちばん合うもの）。各音から、いちばん近いグリッドの位置までの距離を足す
3. 全部の窓・パートの距離を足して、音の数で割る（グリッドごとの「平均のずれ」。単位はステップ）
4. 次の 3 つを全部満たすときだけ、三連にする

| 条件 | 値 | 何を防ぐか・根拠 |
|---|---|---|
| 音の数 | 32 個以上（`GRID_FEEL_MIN_ONSETS`） | 短い音源・音の少ない曲での、偶然の一致 |
| 16 分からのずれ | 平均 0.08 ステップ以上（`GRID_FEEL_MIN_STRAIGHT_ERROR`） | 拍の頭だけで鳴る曲（4 分音符だけ、同じ裏の位置だけ）は、どちらのグリッドにも合う。両方のずれが揺らぎだけになるので、比だけで決めると、偶然で三連になる。三連だけの曲の 16 分からのずれは 0.17〜0.22、拍の頭の多いシャッフルで 0.11〜0.17 |
| 三連からのずれ ÷ 16 分からのずれ | 0.5 以下（`GRID_FEEL_RATIO`） | でたらめな位置の音は、間隔の狭い 16 分のほうによく合う（平均のずれは、16 分 0.20・三連 0.26）ので、迷う曲は 16 分に倒れる。0.5 以下になるのは、音のおよそ 4 分の 3 以上が三連の位置に在るときだけ |

窓ごと・パートごとにずらしてよいのは、次のずれを打ち消すため。どれも、窓の中ではほぼ一定のずれになる。

- **テンポの推定の小さな誤差。** グリッドは、平均のテンポの等間隔。0.5% の誤差で、16 小節あとには 16 分音符 1 個強ずれる。
  曲全体を 1 つのグリッドに当てると、後ろの音が全部「グリッドに合わない音」になり、どの曲も見分けられなくなる
- **1 拍目の位置の誤差、オンセット検出の遅れ。** オンセット検出は、本当のアタックから 1〜2 フレーム（23〜46 ミリ秒）ずれる
- **パートごとの遅れの違い。** ドラムはオンセット検出、ほかのパートは basic-pitch で、遅れ方が違う

ずらしてよいことで、取り違えが増えないか: ずらした三連のグリッドが、16 分の位置の並びにぴったり合うのは、
音の間隔がどれも 4 ステップ（1 拍）の倍数のときだけ（そのときは 16 分にもぴったり合い、上の 2 つ目の条件で外れる）。

### 合成した音の始まりで確かめた結果

1 拍の中の決まった位置に音を置き、1 音ごとに揺らぎ（標準偏差）を足した。5〜20 通りの乱数で、どれも同じ結果。
数は「16 分からのずれ / 三連からのずれ」（120 BPM。1 ステップ = 125 ミリ秒）。

- **三連を見分けられるのは、揺らぎが 1 ステップの 1 割ほどまで**（80 BPM で 15〜20 ミリ秒、120 BPM で 10〜15 ミリ秒、

### 曲全体か、パートごとか

合成した 4 つの曲（パートごとに刻みと揺らぎを変えた。各 30 通りの乱数）で、決め方を比べた。

| 曲 | 曲全体で決める | パートごとに決める |
|---|---|---|
| シャッフルの曲（ドラム・ベースは揃い、ボーカルは揺らぎ 25 ミリ秒、ピアノは拍の頭だけ） | 三連（30/30） | ドラム 三連、ベース 三連（28/30）、**ボーカル 16 分、ピアノ 16 分** |
| 三連の曲（ドラムは三連、ベースは 4 分だけ、ボーカルは揺らぎ 20 ミリ秒） | 三連（30/30） | ドラム 三連、**ほかは 16 分** |
| ふつうの 8 分の曲（ボーカルだけが揺れる） | 16 分（30/30） | 全部 16 分 |
| ふつうの 8 分の曲で、ギターだけが三連のフレーズ | 16 分（30/30） | **ギターだけ 三連** |

- パートごとに決めると、三連の曲で、揺れの大きいパート・音の少ないパートが 16 分になり、同じ曲のお手本どうしで
  グリッドが食い違う（ボーカルの裏が 3、ドラムの裏が 8/3）。曲全体で決めると、揃ったパートが決め手になる
- 曲全体で決めると、「ふつうの曲の中の、1 つのパートだけの三連のフレーズ」は 16 分に丸まる（これまでと同じ結果）。
  勧められていた決め方でもあり、こちらを選んだ

### 限界・確かめられていないこと

- **実曲では、1 回も確かめていない。** 値（32 個・0.08・0.5・窓の長さ）は、合成した音の始まりと、合成した音声でしか
  確かめていない。分離したステムの音の始まりの揺らぎ（分離の質、人の演奏の揺れ、basic-pitch の誤検出）が、合成より
  大きければ、三連の曲が 16 分のままになる。逆の取り違え（ふつうの曲を三連にする）は、でたらめな位置の音が
  16 分に倒れるので起きにくいはずだが、実曲では測っていない
- **テンポを 2/3 倍に取り違えた曲**（付点 4 分を 1 拍と取った。[grid-estimation.md](grid-estimation.md) の「何を直したか」の 3）では、
  本当の 8 分音符が、取り違えたテンポの三連の位置（4/3 ステップおき）に並ぶので、三連になる。取り違えたグリッドの上では
  そのほうが原曲の位置に近いが、直すべきはテンポ（グリッドの確認・補正の窓で直して、もう一度パートに分ける）
- **テンポを半分に取り違えた三連の曲**は、本当の三連が、取り違えたテンポの 16 分の三連（1 拍 6 つ）になるので、16 分のまま
- 曲の途中でグリッドが変わる曲（前半が 8 分、後半がシャッフル）は、音の多いほうが 4 分の 3 に届かなければ 16 分
- 16 分の三連・32 分音符・5 連符は、採譜では出ない。三連のグリッドに丸めた曲では、16 分の刻み（1・3）が、
  近い三連の位置（4/3・8/3）へ動く
- 画面が `grid_feel` をどう使うか（練習の刻み、お手本の見せ方）は、画面の側の決定
- 判定の根拠の数（グリッドごとのずれ）は、API の結果には載せていない（`detect_grid_feel` の戻り値には在る）

## お手本を見ながら打ち込む

お手本と打ち込みを、ピアノロールの上でつなげてある。

- **このパートを練習する**: パートの一覧（「学ぶ」の「曲とパート」）か、パートのトラックの見出しの「練習する」で、
  練習のトラック（「ベースの練習」。`role: 'practice'`、`practiceOf` がパートのトラック）を作るか選び、
  ピアノロールで開いてそのパートのお手本を重ね、お手本の在る高さと最初の小節までスクロールし、
  差分チェックの組を「お手本 = パート、打ち込み = 練習のトラック」にし、パートの音声を鳴るようにする。
  練習のトラックをパートのトラックと分けたのは、パートの音声と自分の打ち込みを別々にミュートできるようにするため（暫定）
- **お手本の重ね表示**: ピアノロールの見出しの「お手本を重ねる」で、お手本のノートを薄く重ねる。
  既定では、開いているトラックがお手本を持っていればそれを、練習のトラックならそのパートのお手本を重ねる。
  自分で一から打ち込むトラックでは、お手本にするトラックを選ぶ。お手本は見るだけで、押しても反応しない
  （下のグリッドに届くので、お手本をなぞってダブルクリックすれば自分のノートが入る）
- **指摘から移動**: 差分チェックの指摘を押すと、比べた打ち込みのトラックがピアノロールに開き、
  再生位置がその拍へ移り、タイムラインとピアノロールがその小節まで横に、ピアノロールはその音の高さまで縦にも動く

## カルテとピアノロールの小節番号（2026-11 に直した）

**直す前の不具合。** カルテは実測のビートと 1 拍目の位置（`grid.downbeat_offset_sec`）で小節を数える
（[grid-estimation.md](grid-estimation.md)）。ピアノロール・タイムライン・再生は 0 秒から整数の BPM で数え、
採譜（`decompose.py`）も 0 秒から、カルテとは別に推定した整数の BPM で数えていた。1 拍目が 0.75 秒に在る曲では、
「カルテの 3 小節」（4.75 秒）はピアノロールでは 3 小節目の頭から 3/8 小節ずれた場所だった。
カルテのコードを見ながら打ち込むと、番号どおりの場所に置いても音がずれる。

**決めたこと（暫定）。** プロジェクトのグリッドを、カルテのグリッドに合わせる。

| 項目 | 決定 | 理由 |
|---|---|---|
| グリッドの持ち方 | テンポ（小数 2 桁）・拍子・1 小節目の位置（`gridOffset` 秒）の 3 つ。ピアノロールのステップ 0 は `gridOffset`。再生・書き出し・メトロノーム・タイムラインの小節番号・MIDI 入力の録音位置も、ここから数える（`web-ui/src/lib/grid.ts`） | 番号の付け方を 1 か所にまとめると、カルテ・ピアノロール・タイムライン・差分チェックの番号が同じになる |
| 曲を取り込んだとき | カルテのテンポ・拍子・1 拍目の位置を、そのままプロジェクトのグリッドにする | 3 つの案（下）のうち、画面に出る番号がどこでも一致するのはこれだけ |
| 採譜 | パート分離に、プロジェクトのテンポと `grid_offset` を渡す。採譜はステップを `grid_offset` から数える（`decompose.seconds_to_step`） | お手本がピアノロールのグリッドにそのまま載る。秒から数え直す（二重に丸める）とステップが 1 つずれることがある |
| 1 小節目より前（弱起） | 採譜した音のうち、1 小節目より前に始まるものは置かない。タイムラインには、その区間の拍の目盛りを番号なしで描く | ピアノロールは負のステップを持てない。カルテも 1 小節目より前を数えていない。グリッド推定は 1 拍目を曲頭から 1 小節未満の位置に置くので、落ちるのは最大でも 1 小節ぶん |
| テンポの精度 | 小数 2 桁（以前は整数に丸めていた） | 128.3 を 128 に丸めると、3 分の曲の終わりで 0.4 秒（16 分音符 3 つぶん）ずれる |
| パートに分けた後でグリッドを直したとき | プロジェクトのグリッドは変えない（お手本は直す前のグリッドで採譜してある）。直した旨と「もう一度パートに分けると合う」をステータスバーに出す。分け直すときは、カルテのグリッドを当ててから採譜する | グリッドだけ変えると、お手本と打ち込みが原曲の音からずれる。番号がずれても、カルテやガイドからの移動は秒で行うので、場所はずれない |
| カルテ・ガイドからの移動 | 小節番号ではなく、カルテの実測のビート列から引いた秒で移る（`chartBarToSec`） | テンポが揺れる曲や、上の「直したとき」でも、カルテが指す音の場所へ行ける |
| 保存したプロジェクト | `gridOffset` を保存する。以前の版のプロジェクト（`gridOffset` が無い）は 0 として読む | 以前のノートは 0 秒から数えて置いたものなので、0 で読めば同じ場所に鳴る |
| 言語化（`coach_explain`） | `grid_offset_sec`（ステップ 0 の位置）を受け取り、ステップを秒に直すときに足す。無ければ 0（以前と同じ） | 引き続き秒で突き合わせる（テンポ揺れ・グリッドを直した場合に強い）。画面の差分チェックの小節番号は、ピアノロールと同じステップから数えるので一致する |

**ほかの案と、選ばなかった理由。**

- **秒で変換するだけ**（カルテ↔ピアノロールの境目ごとに秒を通す）: 移動は正しくなるが、画面に出る番号は
  カルテとピアノロールで違ったまま。「5 小節目のコードは G」と読んで、ピアノロールの 5 小節目に置くと間違う
- **採譜だけカルテのグリッドに合わせる**: ピアノロールの再生と目盛りが 0 秒からのままなので、お手本が原曲とずれて鳴る

**確かめているテスト。** `test/back/test_decompose.py` の `TestChartAndPianoRollBars`（1 拍目が 0.75 秒の合成音で、
グリッド推定 → カルテの 3 小節目の頭で鳴る音を採譜 → ピアノロールの 3 小節目の頭（ステップ 32）に置かれる。
0 秒から数えると置かれない）、`web-ui/src/__tests__/grid.test.ts`（カルテの N 小節とピアノロールの N 小節の時刻が一致する）、
`web-ui/e2e/learn.spec.ts`（1 拍目が 0.75 秒のカルテで、タイムラインの 1 小節目の線が 0.75 秒の位置に在り、
コードの 3 小節目を押すとピアノロールの再生位置の線がステップ 32 に来る）。

## 言語化（差分の説明）

差分の一覧は「どこが違うか」までしか言わない。そこから「どんな傾向の違いか、音楽的になぜ
そうなったと考えられるか、まず何を見直すか」を言葉にする。第2層（再現ガイド）と同じ仕組みで、
同じ保証を付けてある（[reproduction-guide-design.md](reproduction-guide-design.md)）。

### 原則の守り方

**DSP が事実を出し、LLM は言語化だけをする。LLM は音符を 1 つも出力しない。**

| 仕組み | 何を防ぐか |
|---|---|
| 差分は、画面が送ってきた結果を使わず、ノートからサーバの側で計算し直す | 事実でないものを「事実」として LLM に渡すこと |
| 数えれば決まることは、コードが計算して渡す（遅れと早まりの数、拍の頭か裏か、半音の差、その音がコードの何度か、キーの音階に在るか） | LLM の数え間違い・度数の言い間違い（第2層で、機械的な計算を LLM にさせると間違えた） |
| 出力の形を Structured Outputs で固定する。持てるのは説明文と、指摘の ID・小節番号だけ | 音符のデータを返すこと。形の上で入れる場所が無い |
| 指摘の ID・小節への参照を事実と突き合わせ、実在しないものは落とす | 存在しない場所へのリンク |
| 説明文のオクターブつきの音名（E2 など）を事実と突き合わせ、事実に無い音を書いた点は点ごと落とす。全体の要約と「最初にやること」に書かれていたら、その欄を決まった文に差し替える | 新しい音の提案（「ここに A2 を入れる」）。お手本にも打ち込みにも無い音は、画面に出ない |
| 参照が 1 つも残らない点は落とす。点が 1 つも残らなければ失敗にする | 差分の結果と結び付かない一般論 |
| そのほかの音名・コード名・小節番号で事実に無いものを「未確認の語」として返す | 事実に無いコードや場所を説明文に紛れ込ませること（第2層と同じ見張り。遮断ではない） |

第2層より 1 段きびしいのは、オクターブつきの音名だけ。「E2」のような書き方は、ほかの意味に読める
場面がほとんど無い（第2層で遮断にしなかった理由は「A メロ」のような誤検出）。高さで比べるので、
同じ音の別の書き方（A#2 と B♭2）は同じに扱う。コード名の「G7」は「G のオクターブ 7」と同じ形になるので、
事実に在るコード名と一致するものは音名として数えない。

### LLM に渡す事実

`coach_explain.build_facts` が組み立てる。音声もファイル名も渡さない。

| 項目 | 中身 |
|---|---|
| `summary` | 全体の件数（`coach_diff` と同じ）。割合は百分率に直してある |
| `tendencies` | 種類ごとの偏り。位置のずれは遅れ・早まりの数と平均、長さは長い・短いの数、高さの違いは高い・低いの数と半音ごとの数、抜けと余分なノートは拍の頭・裏の数と拍ごとの数。**全部の指摘から数える** |
| `bars` | 小節ごとの種類別の件数（60 行まで。超えるときは、重い小節と件数の多い小節を残す） |
| `issues` | 指摘の表（**40 件まで**）。ID、小節、拍、種類、お手本の音、打ち込みの音、半音の差、位置のずれ、長さの違い。`total` が全件の数。小節と拍は整数。位置のずれと長さの違いは、整数のノートでは整数、小数のノート（三連符など）のときだけ小数 2 桁（上の「小数の位置と長さ」） |
| `worst_bars` | 指摘が重い順の小節（`coach_diff` と同じ） |
| `key` `sections`、`issues` の `chord` `expected_role` `actual_role` | カルテが在るときだけ（下の「カルテとの突き合わせ」） |
| `velocity` | お手本が MIDI ファイルから読み込んだもののときだけ（上の「強さの違い」）。無いときは、項目そのものが無い |

- **指摘の ID** は、`coach_diff.diff_notes` の `bars[].issues[]` を上から数えた番号（`i1` `i2` …）。
  `POST /api/coach/diff` の結果を同じ順に数えれば、画面の側でも同じ ID になる
- **指摘が 40 件を超えるとき**は、一部だけを渡し、全体は `summary` `tendencies` `bars` で伝える。
  選び方は、画面の一覧と同じ並び（重い小節が先、あとは小節順）で、種類ごとに枠を分けて取り、余った枠を
  上から埋める。そのまま上から取ると、1 種類だけで埋まることが在るため（ある区間を丸ごと打ち込んで
  いないと、抜けだけで 40 件になる）
- 同じノートからは、いつも同じ事実（同じバイト列）になる。これを保存の鍵に使う

### カルテとの突き合わせ

リクエストに `chart_id` を付けるとキーを、さらに `bpm`（お手本を採譜したときのテンポ）も付けると、
その場のコードとセクションを事実に足す。

- **カルテの小節番号は使わない。** 画面はふつうカルテのテンポと 1 拍目の位置をピアノロールに使うので番号はそろうが
  （上の「カルテとピアノロールの小節番号」）、テンポが揺れる曲や、パートに分けた後でグリッドを直した場合はずれる。
  そこで、ピアノロールのステップを秒に直し（`grid_offset_sec` + ステップ × 1 ステップの秒）、カルテのコード・
  セクションの秒の範囲と突き合わせる。`grid_offset_sec` が無いときは 0（以前の、0 秒から数えるピアノロール）。
  LLM に渡す小節番号は、すべてピアノロールの番号（画面が移動に使う番号）
- `bpm` が無ければ秒に直せないので、キーだけを使う
- コードは、ステップの真ん中の時刻で引く。採譜はノートの頭をステップに丸めているので、コードの
  変わり目に在る音が、丸めで手前のコードに入るのを避けるため
- 音ごとに、その場のコードの何の音か（ルート・3度・5度・7度）、コードの音でなければキーの音階に
  在るか（コード外・キー内 / コード外・キー外）を計算して渡す。キーの音階は、メジャーと自然的短音階
- 確信度は、第2層と同じ 3 段階（確実 / たぶん / 自信なし）に直して渡す

### 出力の形と、API が返す形

LLM の出力（`COACH_SCHEMA`）は `summary`、`points[]`（`title` `observation` `cause` `fix` `issue_ids[]`
`bars[]`）、`next_step`、`next_step_bar`。検証のあと、API は次の形で返す。

- `summary`: 全体の傾向（2〜3 文）
- `points[]`: 見直すとよい点。1〜3 個、直す効果が大きい順。`title` / `observation`（どんな傾向か）/
  `cause`（なぜと考えられるか。推測なので断定させない）/ `fix`（どこを何と見比べるか）/
  `refs[]`（`{issue_id, bar, beat, kind}`。指摘を指すものが先、あとに小節だけを指すもの。
  小節と拍はサーバが引いて付けるので、画面はそのまま移動に使える）
- `next_step` と `next_step_bar`: 最初にやること 1 つと、その小節
- `dropped_refs` `dropped_points`（落とした参照・点の数）、`unverified_terms`（未確認の語）、
  `replaced`（決まった文に差し替えた欄の名前）

言い方の約束（指示文に書いてある）: 「お手本」と呼び、「正解」「答え」とは書かない。打ち込みを
「間違い」と決めつけず「お手本と違っています」と書く。お手本は自動採譜の結果で原曲どおりとは
限らないので、お手本の音のほうが不自然に見えるときは、採譜の誤りかもしれないと添える。
励ましやほめ言葉は書かない。

### Claude を呼ばない場合

傾向と言えるものが無く、呼んでも一覧を言い直すだけになるときは、決まった文を返す
（`rule_response`。応答の `source` が `"rule"`、費用は 0、記録もしない）。

| `reason` | 条件 |
|---|---|
| `no_diff` | 違いが無い |
| `velocity_only` | 高さ・位置・長さは全部合っていて、強さだけが違う（強さを比べたお手本のときだけ） |
| `no_attempt` | 打ち込みのノートが 1 つも無い |
| `few_notes` | お手本が 4 ノートより少ない |
| `few_issues` | 違いが 3 か所より少ない |

### 費用

第2層と同じ仕組みを、同じ部品で使う（[reproduction-guide-design.md](reproduction-guide-design.md) の「費用」）。

| 仕組み | 第3層での中身 |
|---|---|
| 説明の保存 | 鍵は、事実の指紋 + モデル + 思考の深さ + 指示文と出力の形の指紋。同じノート・同じ条件なら Claude を呼ばない。置き場は `results/coach/cache/`（`guide_cache` の `kind="coach"`） |
| 同時に走らせない | 説明の呼び出しを 1 つずつ通す（連打・二重送信で 2 回呼ばない） |
| 1 日の上限 | **再現ガイドと同じ 1 つの枠**（既定 20 回）。再現ガイドと説明を合わせて数える |
| 使用量の記録 | 再現ガイドと同じ `results/guide/usage.jsonl`。どちらの呼び出しかは `feature`（`guide` / `coach`）で見分ける。ノートも説明文も残さない |
| モデルと思考の深さ | 第2層と同じモデル（`llm_settings.model()`）、思考の深さは `low` |
| 入力を絞る | 指摘は 40 件まで、小節の表は 60 行まで。上限まで渡しても、指示文・事実・出力の形を合わせて 7,000 文字ほど（カルテ無しのとき） |
| 入力の量の確認 | 設定の `max_input_tokens` を超えるときは、呼ばずに知らせる（上の上限が在るので、設定を下げない限り当たらない） |
| プロンプトキャッシュ | 指示文の後ろに区切りを打つ。事実は毎回変わるので、効くのは「直して比べ直す」を 5 分以内に続けたときの、指示文と出力の形のぶんだけ |

### API

`POST /api/coach/explain` と `POST /api/coach/explain/saved`（Claude を呼ばずに返せるものだけを返す。
画面が、お手本と比べた直後に呼ぶ想定）。本文は JSON で、`reference` `attempt`（必須）、`steps_per_bar`
`steps_per_beat` `timing_tolerance`（`/api/coach/diff` と同じ）、`chart_id` `bpm`、`regenerate`。
`reference_source`（お手本の出どころ）は、差分と説明のどちらの API も受け取る。`"midi"` のときだけ強さを比べる。
失敗の返し方（ステータスと `detail` の `{message, code}`）は、再現ガイドと同じ。

### 決めたこと（どれも暫定）

| 項目 | 決定 | 理由 |
|---|---|---|
| 入力 | ノートを受け取り、差分をサーバで計算し直す | 画面が送る「差分」を信じると、事実でないものが LLM に渡りうる |
| 渡す指摘の上限 | 40 件 | 画面の一覧の上限と同じ。傾向は件数の集計で伝わるので、1 件ずつは例として足りる数でよい |
| 点の数 | 1〜3 個 | 細いパネルで読みながら手を動かす。多いと「まず何を」がぼやける |
| 事実に無い音 | 点ごと落とす（要約と「最初にやること」は差し替える） | 「LLM は音符を出さない」を、説明文の中でも守るため。応答ごと捨てると、費用だけかかって何も出ない |
| 参照の無い点 | 落とす | 画面は、点から小節へ移動できる前提で出す |
| 違いが 3 か所より少ないとき | Claude を呼ばない | 傾向とは言えず、一覧を読めば足りる |
| 上限と記録 | 再現ガイドと共通 | 利用者から見れば、どちらも同じ「Claude の費用」 |
| 思考の深さ | `low` | 第2層に合わせた。第2層は実測で決めたが、こちらは**測っていない** |
| カルテ | 任意。小節番号ではなく秒で当てる | カルテとピアノロールのグリッドが別物のため |
| 種類の呼び名 | 画面の一覧と同じ「高さの違い」「余分なノート」 | お手本は正解ではないので、「間違い」と言わない。呼び名は [ui-terms.md](ui-terms.md) に合わせる（当初は「音の違い」「余分な音」だったが、画面の見直しで一覧と合わせた） |

### 画面

差分チェックの結果（正確さ・種類ごとの件数・まず見るとよい小節）の下に出す（`CoachPanel.tsx` の `ExplanationSection`）。

- **比べた直後**に `POST /api/coach/explain/saved` を呼ぶ（Claude は呼ばない）。保存済みの説明か、Claude に頼むまでもない
  ときの決まった文が返れば、押さなくても最初から出す
- 無ければ「Claude に説明してもらう」。出したあとは「説明を作り直す（費用がかかります）」（押したときだけ `regenerate`）。
  費用まわりの表示（何を送るか、1 回ごとの使用量と概算の費用、今日の累計と上限、API キーと上限の設定、保存済みの旨）は
  再現ガイドと同じ部品（`ClaudeParts.tsx`、`lib/claude-usage.ts`）
- **説明の材料は、画面に出ている差分と同じノート**（比べたときのノートを控えておく）。比べたあとにノートを直しても、
  説明の指摘の ID が一覧とずれない。直したら、比べ直す
- 点ごとに「傾向」「考えられる理由」「直し方」と、場所の札（`refs`）。札を押すと、その拍へ移り（ピアノロールに打ち込みの
  トラックを開く）、指摘を指す札なら一覧の該当する行を示す（ID は `bars[].issues[]` を上から数えた番号。`lib/coach.ts` の
  `issuesById`）。「最初にやること」にも、その小節への札を付ける
- 事実に無い語（`unverified_terms`）は、再現ガイドと同じく黄色の注意で出す。落とした点が在れば、その数を添える
- 決まった文（`source: 'rule'`）は「最初にやること」だけを出し（要約は、すぐ上の正確さ・件数の言い直しなので出さない）、ボタンも費用の表示も出さない（理由を一言添える）
- カルテは、お手本と同じ曲のときだけ添える（`chart_id` `bpm` `grid_offset_sec`）。パート分離のときにカルテのグリッドで
  採譜していて、いまのカルテがそのカルテのとき（`lib/learn.ts` の `chartIdOfParts`）。別の曲を取り込んだあとの古いパートや、
  画面を開き直したあと（覚えていない）には添えない

### 確かめられていないこと

- **本物の Claude での出来。** 偽のクライアントでしか動かしていない。出力の形が API に受け付けられるか、
  指示文で狙った書き方（傾向をまとめる、断定しない、音を提案しない）になるか、落とす点がどのくらい出るか、
  1 回あたりの費用、プロンプトキャッシュが効くか（区切りまでが、キャッシュできる最小の長さを超えるか）は未確認。
  `scripts/guide_probe.py` に、説明を試すコマンドはまだ無い
- 思考の深さ `low` で足りるか
- 「原因」の質。事実に手がかりが無いときに、もっともらしい理由を作らないか
- カルテとの突き合わせは、お手本を採譜したあとでテンポを変えていない前提。変えていると、秒がずれる
  （サーバからは見分けられない）。お手本のトラックと同じ曲のカルテかどうかも、画面が判断して送る

## 学習の記録（2026-11 に実装。置き場の決定は暫定）

「お手本と比べる」を押すたびに 1 件残し、差分の段に直近の一致率・前回との差（「一致 67% 前回より +34%」）・推移・直近 5 回を出す
（`web-ui/src/components/LearnHistory.tsx`）。プロジェクトを保存すると `.bunri` の `learning_history` 表に入り、開くと戻る。

| 項目 | 中身 |
|---|---|
| `recordedAt` | 比べた時刻（ISO 8601） |
| お手本 / 打ち込みのトラック | 画面ではトラックの ID、ファイルでは並びの番号（`practiceOf` と同じ持ち方）。`part`（`bass` など）も持つ（トラックを消しても、どのパートか分かる） |
| `startBar` `endBar` | 比べた範囲（小節、両端を含む）。範囲を指定しない比較は、お手本のノートの最初から最後まで |
| `referenceCount` `matched` `matchRate` | 範囲の中のお手本のノートの数、合っていた数、一致率 |
| `counts` | 違いの種類ごとの件数（抜け・高さの違い・オクターブ違い・余分なノート・位置のずれ・長さの違い） |
| `explanationId` | Claude の説明の保存の鍵（説明を作った・保存済みを出したとき）。プロジェクトに説明の写しも入る |
| `barStats` | 小節ごとの結果（2026-11-18 に足した）。範囲の中の、お手本のノートが在る小節ごとに `{bar, referenceCount, matched}`（小節順）。差分の結果の `bar_stats` をそのまま持つ。足す前の版が残した記録には無い（`null`）。下の「練習の地図」 |

**一致率の決まり**（練習画面もこれに合わせる）: 範囲の中のお手本のノートのうち、打ち込みと合っていたノートの数 ÷ 範囲の中のお手本のノートの数。
「合っていた」は差分チェックと同じ（同じ高さで、位置のずれが 16 分音符 2 個以内。長さの違いと許容内のずれは合っている側に数える）なので、
値は `coach_diff.diff_notes` の `summary.accuracy` そのもの。範囲で比べるとき（練習画面のループ）は、範囲の中のノートだけを差分チェックに渡す。
前回との差は「同じお手本・同じ打ち込みのトラック（範囲を渡せば同じ範囲）の、1 つ前の記録」との % の差（ポイント）。

練習画面（見出しの「前回より」。下の「練習画面」）は `web-ui/src/lib/learn-history.ts` の `useMatchSummary(練習のトラックの ID, お手本のトラックの ID?, 範囲?)` で
`{ percent, previousPercent, deltaPercent, bestPercent, attempts, latest }` を受け取る（`deltaText()` が「前回より +8%」を作る）。
記録を足すのは `useDaw().recordLearnAttempt(attemptFromDiff(差分の結果, {..., range}))`。

**置き場を `.bunri` にした理由（暫定）**: 選択肢は `.bunri` / アプリのデータ置き場の別の DB / RDB（アカウント層）。

- 記録が指すもの（トラック・小節・お手本）は、その曲のプロジェクトの中にしか無い。別の DB に置くと、プロジェクトとの結び付け
  （ファイルを移した・別名で保存した・別の PC で開いた）を別に作ることになり、結び付けが切れた記録が残る
- 第1層の設計で、ドキュメント層を「楽曲プロジェクト（カルテ・将来はトラック/ノート/進捗）」と決めてある。進捗はこの層
- ファイルを人に渡せば、記録も一緒に渡る（先生に見せる、別の PC で続ける）。消すときもファイル 1 つ
- 弱み: 保存しないで閉じると、その間の記録は残らない。記録が増えると「保存していない変更」の印を付け、閉じる前に尋ねて補う。
  曲をまたいだ上達の集計（RDB）は、アカウント層を作るときに、各プロジェクトの記録から集める

## 練習の地図（2026-11-18 に実装。集計の決まりは暫定）

学習の記録は「比べた回」の一覧で、曲のどこを比べ終えていて、どこが手つかずかは分からなかった。そこで、記録に小節ごとの結果を
持たせ、パートごと・構成の区間ごとの一致率を、升の並び（地図）で出す。LLM は使わない（アシスタントのツールにも足していない）。

### 小節ごとの結果（事実を出す側）

`coach_diff.diff_notes` の結果に `bar_stats` を足した。お手本のノートが在る小節ごとに `{bar, reference_count, matched}`（小節順）。

- 小節は、**お手本のノートが始まる位置**で決める（`int(step // steps_per_bar) + 1`。指摘の `bar` と同じ。ステップが小数でも整数になる）。
  打ち込みが隣の小節へずれて合った組も、お手本の小節に数える
- `matched` は一致率と同じ数え方（同じ高さで、位置のずれが許容以内で組になったお手本。長さの違いと許容内のずれも、合っている側）。
  全部足すと、`reference_count` は `summary.reference_count`、`matched` は一致率の分子になる（テストで確かめている）
- **既存の欄は変えていない**（`summary` `bars` `worst_bars` `velocity`）。`coach_explain.build_facts` は使う欄を名前で取り出すので、
  言語化に渡す事実・保存の鍵・版には影響しない（`bar_stats` は事実に入らない）
- 範囲で比べるとき（練習画面の区間ループ）は、範囲の中のノートだけを、ステップを変えずに渡すので、小節番号はピアノロールの番号のまま

画面は、記録を作るとき（`attemptFromDiff`）に `bar_stats` を `barStats` として持たせる。記録の `matched` は、`barStats` の合計
（以前は一致率から戻していた。同じ値になる）。

### 保存の形

`.bunri` の `learning_history` 表に、列 `bar_stats`（TEXT）を足した。中身は JSON で `[[小節, お手本のノートの数, 合っていた数], ...]`（小節順）。
小節ごとの結果を持たない記録は NULL。文書（画面と sidecar のあいだの JSON）では `barStats: [{bar, referenceCount, matched}] | null`。

- **形式の版（`format_version` 2.0）は上げていない。** 列を足しただけで、前の版の bunri は知らない列を読み飛ばす
  （[song-chart-design.md](song-chart-design.md)「プロジェクトの保存」の前方互換の決まり。ノートの強さの列を足したときと同じ扱い）
- **以前のファイルも開ける。** 列が無いファイルは、列を読まずに `barStats: null` として読む。開くときに作業用の写しを上げる
  （`migrate`）と列が足されるが、以前の記録は NULL のまま。読めない値（こわれた JSON）も、持たない記録として読む
- 前の版の bunri で開いて保存し直すと、小節ごとの結果は落ちる（一致率などの、もとからの欄は残る）

### 集計の決まり（`web-ui/src/lib/practice-map.ts`。純粋な関数）

| 項目 | 決定 | 理由 |
|---|---|---|
| 行 | お手本のノートを持つトラック（パートの種類は決め打ちしない） | ドラムなど、あとからお手本を持つようになったパートも、そのまま行に出る |
| 数える記録 | 「そのパートがお手本、その**練習のトラック**が打ち込み」の記録だけ（`referenceId` と `attemptId` の両方が合うもの）。練習のトラックがまだ無いパートは、どの升も「まだ比べていません」 | 升を押すと開くのは、そのパートの練習画面。差分チェックで別のトラック（お手本を写したパート自身など）と比べた結果を混ぜると、練習の進み具合ではなくなる |
| 古い記録 | トラックを消した・パートを分け直した記録は、ID が合わないので数えない（保存すると、消したトラックは `null` になる。もとからの決まり）。パートの名前（`part`）では結び直さない | 分け直したあとのお手本は、前のお手本とは別物。名前で結ぶと、別のお手本の一致率を出すことになる |
| 小節の値 | その小節を含む、**いちばん新しい**記録の結果（記録は古い順に並んでいる） | 直したあとの結果を見せる。良かったときの値は残さない |
| お手本が変わっていたら | 記録が持つその小節の「お手本のノートの数」が、いまのお手本の数と違えば、その小節には使わない | 同じトラックのまま拍子を変えた・お手本を差し替えた、のような場合に、嘘の値を出さない |
| 以前の記録（小節ごとの結果が無い） | 範囲全体の一致率を、範囲の中の小節に**一様に当てはめる**（小節の合っていた数 = 一致率 × その小節のお手本のノートの数）。範囲の中のいまのお手本のノートの数が、記録の数と違えば使わない。升の説明に「以前の記録なので、小節ごとの内訳はありません（比べた範囲全体の一致率です）」と添える | 捨てると、以前のプロジェクトを開いたときに、比べたはずの区間が全部「まだ比べていません」になる。範囲がそのまま 1 つの区間なら、当時の一致率と同じ値になる |
| 区間の値 | 中の小節の合計（合っていた数 ÷ お手本のノートの数）。**比べていない小節は、合計に入れない**。小数 4 桁に丸めてから整数の % にする（差分の `accuracy` と同じ丸め方） | 区間の一部だけを比べたときに、練習画面の「一致」・学習の記録の % と同じ数になる。比べていない小節を 0 として入れると、別の数字が 2 つ出る |
| 状態 | お手本のノートが無い / まだ比べていない（ノートは在るが、どの記録も掛かっていない）/ 途中（ノートの在る小節の一部だけ比べた）/ 一致 N%（全部比べた）。お手本のノートが無い小節は、小節の数に入れない | 弾くものが無い小節は、比べようがない |
| 段階 | 80% 以上 / 50〜79% / 50% 未満（`--ok` / `--warn` / `--error`） | 色は 3 つまで。境目は実装者が決めた値で、測っていない |
| 列 | カルテの構成の区間。**秒からプロジェクトの小節に換える**（`lib/practice.ts` の `secondsToBars`。練習画面の「構成」の段・区間ループと同じ換え方で、カルテの小節番号は使わない）。構成が無ければ（自由に作った・カルテの無いお手本）、1 小節目からお手本の最後の小節までを 4 小節ごとに区切る | カルテとピアノロールのグリッドが別でも、同じ音の場所を指す。上の「カルテとピアノロールの小節番号」 |

### 画面

- **地図**（`components/PracticeMap.tsx`）: 「学ぶ」→「差分」の段のいちばん上（差分チェックのパネルの上。進み具合の ⑤ 差分で直す から辿れる）。
  升を押すと、「このパートを練習する」と同じ処理（`practicePart`）で練習画面を開き、区間ループをその区間にする
  （区間の設定は、練習画面の中で区間を変えるのと同じ `updatePractice`。32 小節より長い区間は、はじめの 32 小節）。
  表（`role="grid"`）で、Tab で入り、矢印キー・Home・End で升を辿り、Enter か Space で押す。区間が多いときは、表だけが横にスクロールする
- **練習画面の「構成」の段**: 区間の名前の後ろに、いま練習しているパートの、その区間の一致率を小さく出す（まだ比べていなければ空の枠）。
  比べるたびに記録が増えるので、その場で変わる。区間を押す操作と、ボタンの名前は変えていない（状態は、説明と読み上げの補足に入れた）
- 記録が 1 件も無いときは「お手本と比べると、ここに曲全体の進み具合が出ます」と出し、空の升は出したままにする（升から練習を始められる）
- 升を辿る（どの升にフォーカスが在るか）のは見た目だけの状態で、プロジェクトに入れない。升を押して区間が変わると、
  練習画面で区間を変えたときと同じく、保存していない変更になる

### 確かめられていないこと・扱っていないこと

- カルテの構成の区間の外に在るお手本のノート（構成が曲の終わりまで届いていない、別の曲の MIDI をお手本にした、など）は、どの升にも入らない
- 区間の境目が小節の途中に在ると、その小節は前後の両方の区間に数える（練習画面の「構成」の段の区間ループと同じ）
- 練習のトラック以外と比べた記録（差分チェックで選んだ別のトラック）は、地図に出ない
- 段階の境目（80% / 50%）と、以前の記録を一様に当てはめる扱いは、利用者に確かめていない

## 練習画面: 指摘とノートの色、一致

練習画面（`web-ui/src/components/PracticeView.tsx`、計算は `web-ui/src/lib/practice.ts`）の「比べる」は、
同じ `POST /api/coach/diff` を使う。区間ループが入っていれば、**区間の中で始まるノートだけ**を送る
（お手本も打ち込みも同じ範囲で切る。ステップはそのまま送るので、指摘の小節番号はピアノロールの番号のまま）。
区間の境目のすぐ外へずれたノートは、相手のいない「抜け」「余分」になりうる（暫定。区間の端で数件）。
左パネルの差分チェックと進み具合には、曲全体で比べた結果を別に渡す（区間だけの結果を全体のものとして見せない）。

### 指摘からノートへ

指摘は、お手本のノート（`expected`）と打ち込みのノート（`actual`）を持つ。同じ形（音名・オクターブ・位置・長さ）の
ノートを探して、ノート 1 つ 1 つに印を付ける（`markNotes`）。同じ形のノートが 2 つ在れば、1 つずつ順に結ぶ。
位置のずれと長さの違いは同じ組に 2 件付くことがあるので、組ごとに同じノートへ結ぶ。

| 指摘の種類 | 打ち込みのノート | お手本のノート |
|---|---|---|
| （指摘なし） | 合っている: 緑の縁（`--ok`） | 合っている: 緑の縁で薄く |
| 高さの違い・オクターブ違い | 高さが違う: 黄色（`--warn`）の塗りに斜線 | 指摘を結ぶだけ（見た目はふだんのお手本。一覧から押すと一緒に光る） |
| 位置のずれ・長さの違い | 位置か長さがずれている: 塗りは変えず、黄色の点線の縁。位置のずれは向きの印（‹ 早い / › 遅い） | 合っている（一致に数える） |
| 余分なノート | お手本にない: 赤（`--error`）の塗りと × | — |
| 抜け | — | お手本の抜け: 赤の破線の縁 |

色だけに頼らない（模様・縁・記号・凡例・読み上げの名前）。印の付いたノートは `role="img"` で、名前は
「F2: 高さが違う。1 小節 2 拍目: F2 → お手本は E2」の形（指摘の文は一覧と同じ `issueText`）。
印はノートの並びの番号で持つので、ノートを変えた（書き戻した・元に戻した）ら、ピアノロールが自分で外す。
区間を変えたときも外す。どちらも「ノート（区間）を変えたので、もう一度比べてください」と出す（自動では比べ直さない）。

### 一致

**比べた範囲のお手本のうち、高さが同じで、位置が 16 分音符 2 個以内だったノートの割合**（差分の `summary.accuracy` を
百分率に丸めたもの）。長さの違いと小さな位置のずれは、合っている側に数える。左パネルの「〜% が合っています」と同じ定義で、
範囲だけが違う。お手本は採譜の結果なので「正解率」とは呼ばない（[ui-terms.md](ui-terms.md)）。
比べるたびに学習の記録（下の「学習の記録」）に 1 件足す。範囲は区間ループの小節（区間ループを止めていれば、お手本のノートの
最初から最後まで。差分チェックの段で比べた記録と同じ範囲になる）。見出しには「一致 72% ▲前回より +8%」を出す。前回は
**同じお手本・同じ練習のトラック・同じ区間**の 1 つ前の記録（`useMatchSummary(練習のトラック, パート, 区間)` と `deltaText()`）。
区間を変えて比べると、その区間でははじめての記録になる（曲の別の場所の一致と比べても意味が無いため）。まだ比べていなければ、
いまの区間の前回の記録の値を添える（開き直したプロジェクトでも、どこまでできていたかが分かる）。差分チェックの段の記録の
「前回より」も、最後の記録と同じ範囲どうしで比べる。
