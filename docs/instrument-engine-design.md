# 楽器の音とエンジンの設計

打ち込んだノートを、本物の楽器の音で鳴らすための設計。
bunri の目的は「原曲の音を使わずに、利用者が自分で再現できるよう導く」ことで、
そのためには、打ち込んだ結果が原曲に近い音で鳴る必要がある。

この文書は計画の段階のもの。各 PR を作る中で分かったことに合わせて直す。

## 今の状態 (2026-11-14 時点)

- ピアノロールの再生、書き出し (mixdown)、MIDI 鍵盤の試聴は、すべて **三角波 1 種類** で鳴る。トラックに楽器を選ぶ仕組みが無い
- デスクトップ版の再生と鍵盤の試聴は、Rust の engine が鳴らす (PR 3。下の「再生を Rust に移して分かったこと」)。
  音色は同じ三角波 (仮の音)。書き出しと、ブラウザ (開発用のブラウザ起動・自動テスト) での再生は、画面側の Web Audio
  (`web-ui/src/lib/engine.ts` の `_scheduleTrackNotes` / `mixdown` / `liveNoteOn`)
- Python の GM 音源 (FluidSynth + `MuseScore_General.sf3`) は同梱していない。ツール画面のシンセにしかつながっていない
- ドラムは合成のキック / スネア / クローズドハイハットの 3 音と、固定パターン 4 種だけ (`backend/synth.py`)
- ノートは、強さ (velocity。1〜127) を省略できる項目として持つ (MIDI 鍵盤で弾いたノート、MIDI ファイルから読み込んだノート、
  採譜したお手本に在る。無いノートは 96 として鳴らす)。強さは三角波の音量にだけ効く。ピアノロールでは、選んだノートの強さを
  見出しの「強さ」の欄で直せる (数値、−/＋、Option + ↑↓。直したノートにだけ値を持たせ、触っていないノートは持たないまま)。
  位置は 16 分音符の格子 (`step`) にしか置けない
- 楽曲カルテは音の高さ・リズム・コード・ミックスを持つが、**音色** は持たない。再現ガイドもアプリに在る音を前提にしていない
- Rust の engine (`src-tauri/audio-engine`) は、曲を受け取ってオフラインで WAV に書き出せる (PR 2)。
  アプリの書き出しは、まだこれを使っていない (楽器の音が入る PR 5 で移す)

## 利用者が決めたこと

| 決めたこと | 内容 |
|---|---|
| 優先するもの | **品質。時間はかかってよい** |
| エンジンの置き場 | **ネイティブ (Rust)**。楽かどうかではなく品質で決める |
| 素材の容量 | **上限なし** (全部そろえて 5GB を超えてもよい)。強さの段数やマイク位置は素材のまま使う |

エンジンをネイティブに置く理由: 素材を全部使うと数 GB になる。画面側の Web Audio は素材をメモリに
全部展開するしかなく (float32 で元の 2〜4 倍)、載らない。ネイティブなら、音の頭だけをメモリに置き、
続きをディスクから読みながら鳴らせる (disk streaming)。MIDI 鍵盤を弾いたときの遅れも小さくできる。
[desktop-architecture.md](desktop-architecture.md) で Tauri を選んだ理由の一つ (「後で低レイテンシの
音声エンジンを同じ場所に書ける」) を、ここで使う。

## 方針: 楽器ごとに一番良い作り方を選ぶ

| 楽器 | 作り方 | 理由 |
|---|---|---|
| ピアノ・ドラム・ベース・ストリングス・管・木管 | マルチサンプル (SFZ) | 生楽器は合成では本物に届かない |
| エレキギター | クリーンの録音 (DI) のサンプル + アンプの模擬 | 歪みは弾き方と一緒に変わるので、歪んだ録音を並べるより後段で作るほうが自然 |
| エレピ | 合成 (物理モデル / FM) | 自由に使えるサンプルが非商用ライセンスしか見つからなかった |
| リード・パッド・シンセベース・808 | シンセ | 原曲の音もシンセで作られている。パラメータで寄せられ、ガイドが言葉で説明できる |

## 構成

```
WebView (React)
  │  Tauri command: 曲の内容を渡す / 再生・停止・位置 / 鍵盤の試聴
  │  Tauri event:   再生位置 (30 回/秒程度)・メーター・素材の読み込み状況
  ▼
Rust: src-tauri/audio-engine/src/  (crate 名 bunri-audio。Tauri 抜きでテストできるよう、アプリとは別の crate)
  ├─ song       … engine に渡す曲のデータ (トラック・ノート・クリップ・楽器)
  ├─ engine     … 曲の内容を持ち、ブロックごとに音を作る
  ├─ sampler    … sfizz (C API) を包む。SFZ を読み、ディスクから少しずつ読む
  ├─ tone       … 仮の音 (三角波)。楽器の素材が入る PR 5 まで、ノートと鍵盤の試聴をこれで鳴らす
  ├─ clips      … 取り込んだ音声 (原曲・ステム・録音) の再生
  ├─ mixer      … トラックの音量・パン・ミュート・ソロ、マスター
  ├─ render     … 同じ engine をオフラインで回す (書き出し)
  ├─ audio      … メモリに置いた音声と、WAV の読み書き
  ├─ resample   … サンプリング周波数の変換 (クリップを engine の周波数に合わせる)
  ├─ transport  … 再生の状態 (再生・停止・区間ループ・カウント・メトロノーム・試聴・位置の公開)。音声スレッドで engine を回す
  ├─ synth      … 自作のシンセ (まだ無い。PR 7)
  └─ output     … cpal で音声デバイスに出す
```

Tauri の command / event と engine をつなぐ部分は、アプリの crate に在る (`src-tauri/src/audio.rs`)。
画面の側の口は `web-ui/src/lib/native-audio.ts` で、呼ぶのは再生エンジン (`lib/engine.ts` の `AudioEngine`) だけ。

- **再生・試聴・書き出しは同じ engine を通す。** 聞いた音と書き出した音が食い違わない
- **取り込んだ音声のクリップも Rust で鳴らす。** 楽器だけ Rust、クリップは Web Audio にすると、
  二つの時計がずれる。原曲と打ち込みを重ねて聞く bunri では致命的なので、まとめて移す
- 録音 (`MediaRecorder`) と MIDI 入力 (`midi.rs`) は今の置き場のまま。MIDI 入力は Rust の中で
  engine に直接渡せるようになるので、鍵盤の試聴の遅れが減る

### リアルタイム処理の約束ごと

音声スレッドの中では次をしない (音が途切れる原因になる):

- メモリの確保と解放、ロック (`Mutex`)、ファイルの読み書き、ログ出力
- 画面からの指示は、ロックの無いキュー (例: `rtrb`) で渡す。曲の内容が大きく変わるときは、
  別スレッドで新しい状態を組み立ててから差し替える
- sfizz は自分のスレッドでディスクを読むので、この約束を守れる

### 開発用のブラウザ起動と自動テスト

ブラウザ (`make dev-web` / `make e2e`) では Rust が居ないので、楽器の音は鳴らない。
画面側は「エンジンに渡す口」を一つにまとめ (`lib/native-audio.ts`)、ブラウザでは今の Web Audio (三角波) にフォールバックする。
デスクトップ版でも、Rust の呼び出しが失敗したら、そのセッションのあいだ Web Audio に切り替える。

- 画面の操作 (楽器を選ぶ、ノートを置く) は今まで通り `make e2e` で確かめる
- 音そのものは Rust のテストで確かめる: engine をオフラインで回し、決めた入力に対して
  音量・音の高さ・鳴り始めの位置が合っているかを見る (ビット一致は求めない)
- 窓ごと確かめるのは `make e2e-desktop`

## 曲のデータの変更

| 変更 | 理由 |
|---|---|
| ノートに強さ (velocity, 1〜127) を足す | 生楽器のサンプルは強さで音色が変わる。強さが無いと、どのノートも同じ叩き方になる |
| 位置と長さを 16 分音符より細かく持つ (ティック。1 拍 = 960) | 原曲のノリ (ハネ・もたり) を打ち込めるように。画面の吸着は今まで通り 16 分 |
| トラックに楽器を持たせる | `{ kind: "sampler", id }` か `{ kind: "synth", patch }`。未指定はピアノ |
| お手本のノートにも強さと細かい位置を持たせる | 差分コーチが強さとタイミングのずれも指摘できるように (第 3 層) |

古いプロジェクトは読み込み時に変換する (`step` → ティック、強さは 96)。

強さの項目そのものは、MIDI キーボード入力の仕上げで先に入った (`PianoNote.velocity`、`.bunri` の `project_notes.velocity`。
どちらも省略可で、無ければ 96)。ピアノロールでの編集も先に入った (選んだノートへの数値入力。強さの棒を並べるレーンは無い)。
ここで残っているのは、すべてのノートに強さを持たせる変換と、差分コーチが強さの違いを指摘すること。

## 素材

### ライセンスの決まり

- **CC0 と CC-BY だけを使う。** 非商用 (NC) は使わない。継承 (SA) は、素材を加工して配る必要が出たときに困るので、なるべく避ける
- CC-BY の素材は、作者名と出典をアプリの「ライセンス」画面と `THIRD_PARTY_NOTICES` に載せる
- 取り込む前に、配布元の LICENSE ファイルで確かめる (検索結果や二次情報で済ませない)

|---|---|---|
| ピアノ | Salamander Grand Piano | CC-BY 3.0 |
| ドラム (生) | Virtuosity Drums、Big Rusty Drums (Karoryfer) | CC0 |

### 配り方

- アプリには同梱しない。楽器ごとに、初めて使うときにダウンロードする (Demucs のモデルと同じ扱い)
- 置き場: アプリのデータ置き場の `instruments/<id>/<版>/` (`BUNRI_DATA_DIR` に従う)
- 一覧 (カタログ) を JSON で持つ: id、版、URL、SHA-256、サイズ、ライセンス、作者
- 配布元の URL は変わることがあるので、こちらで GitHub Releases に置き直す (CC0 / CC-BY は再配布できる)。
  1 ファイル 2GB の上限があるので、楽器ごと・必要なら分割して置く
- サンプルは FLAC にして容量を減らす (sfizz は FLAC を読める)
- ダウンロードは途中から再開でき、SHA-256 で確かめる。画面に進み具合を出す

## シンセ

品質の目標: 市販のソフトシンセの基本の音 (リード・パッド・ベース) を、聞いて区別が付かない程度に作れること。

- オシレーター 2 基 + サブ + ノイズ。波形は帯域制限したもの (ウェーブテーブルを音域ごとに用意する、
  または PolyBLEP)。折り返しノイズを出さない
- フィルタ: ラダー (ムーグ型) と状態変数型 (LP / HP / BP)。ゼロ遅延の形で書き、カットオフを速く動かしても崩れないようにする
- エンベロープ 2 基 (音量・フィルタ)、LFO 2 基、ユニゾン (最大 7、デチューンと広がり)、グライド、モノ / ポリ
- 歪みを足す部分はオーバーサンプリングする
- プリセットを用意し、ガイドが名前で指せるようにする (「プリセット『暖かいパッド』で、カットオフを下げる」)

## エフェクト

今のエフェクト (EQ / コンプ / リバーブ / ディレイ) は Python でファイルにかける作り。
打ち込んだトラックにリアルタイムでかけられるよう、Rust 側にも作る。後の PR で扱い、この文書では順番だけ決める。

## 進め方 (PR の並び)

各 PR が終わった時点で、アプリが使える状態を保つ。

1. **試作 (spike)** (済み。下の「試作で分かったこと」): sfizz を `src-tauri` から組み込み、cpal で 1 音鳴らす。macOS (arm64) でビルドでき、
   CI が通り、Salamander のピアノを鍵盤で弾いて遅れとメモリを測る。ここで無理が分かったら設計を見直す
2. **Rust の engine とオフライン描画** (済み。下の「engine を作って分かったこと」): トラック・ノート・クリップを受け取り、
   WAV に書き出せる。テストで音を確かめる
3. **再生を Rust に移す** (済み。下の「再生を Rust に移して分かったこと」): 画面の再生・停止・位置・ループ・
   メトロノームを engine につなぐ。ブラウザではフォールバック
4. **曲のデータの変更**: 強さと細かい位置。古いプロジェクトの変換。ピアノロールで強さを編集できるように
   (選んだノートへの数値入力は、先に入った)
5. **素材のダウンロードと楽器の選択**: カタログ、ダウンロード、トラックごとの楽器選択。まずピアノ 1 つ。
   書き出しも Rust のオフライン描画に移す (聞いた音と書き出した音を同じにする)
6. **楽器をそろえる**: ドラム (キットとドラム用の打ち込み画面)、ベース、ストリングスなど
7. **シンセ** (+ エレピ、808 系)
8. **エフェクトを Rust に**
9. **カルテに音色の手がかりを足す** (第 1 層): 分離したステムから明るさ・アタック・減衰などを DSP で出す
10. **ガイドとつなぐ** (第 2 層): ガイドがアプリに在る楽器・プリセット・パラメータで道筋を示す

9・10 は別の設計書にする。

## 片付けるもの

engine が移り終わったら、次は要らなくなる:

- 画面側の三角波の再生 (ブラウザ用のフォールバックとしてだけ残す)
- Python のシンセ・ドラムマシン・GM 音源 (`synth.py` の該当部分、FluidSynth、`MuseScore_General.sf3` の扱い)

## 試作で分かったこと (2026-11-13、PR 1)

`src-tauri/audio-engine` (crate 名 `bunri-audio`) に sfizz を組み込んで測った。機械は MacBook Air (Apple Silicon)。

| 項目 | 結果 |
|---|---|
| ビルド | sfizz を submodule (`third_party/sfizz`、f5c6e29) から cargo のビルドの中で cmake にかけ、静的にリンクできた。初回は約 1〜2 分。clang 19 以降では sfizz が抱える古い atomic_queue がエラーになるので、その警告だけエラー扱いをやめている |
| Rust とのつなぎ | 既製の crate は無いので、使う関数だけを手で宣言した (bindgen は使わない。数が少なく、libclang が要らない方が楽) |
| 素材 | Salamander Grand Piano V3 の原本 (archive.org、48kHz/24bit、WAV 641 本、1.8GB、CC-BY 3.0 を配布元で確認) |
| 読み込み | 0.37 秒 (2 回目以降は 0.08 秒)。region 641 |
| メモリ | 147MB (プロセス全体の最大)。1.8GB の素材でも、メモリに置くのは各サンプルの頭 (既定 8192 フレーム) だけ |
| オフライン描画 | 音 8 秒を 0.022 秒 (実時間の約 350 倍) |
| リアルタイム | ペダルを踏んで 0.25 秒ごとに 8 音を重ね、声を 197 まで増やしても、バッファ 64 / 128 / 256 フレーム (1.3 / 2.7 / 5.3 ms) のどれでも音の途切れは 0 回。持ち時間の 50% を超えたのは数千回中数回 (一度きりの外れ値) |

### 見つけた落とし穴

- **書き出しでは sfizz をオフラインのモード (freewheeling) にしないと、音の続きが無音になる。**
  実時間の数百倍で回すので、ディスクからの読み込みが追いつかない。sfizz は、データが足りなくなった声を
  「サンプルの終わり」とみなして止める。`render` が描画のあいだだけオフラインのモードにする
  (テスト「書き出しではサンプルの頭より後ろも欠けない」。試しに待たないようにすると、0.17 秒より長い
  ノートが途中で切れ、手元では engine のテスト 28 件のうち 8 件が落ちた。読み込みとの競争なので、
  どれが落ちるかは回すたびに変わりうる)
- オフラインのモードには、コードを読んで見つけた競合がもう一つある (読み込みの依頼がジョブになる前に、
  待つ処理が素通りする)。手元では再現しなかったが、起きると書き出しの一部が黙って欠けるので、
  sfizz に小さな直しを当てている (`audio-engine/build.rs` の `PATCHES`。submodule は本家のまま置き、
  ビルドのときに写してから直す)。本家にも報告したい
- **sfizz は、声が鳴り始めて最初のブロックの境目で、サンプルを 1 フレームぶん止める** (同じ値が 2 回出て、
  そのあとが 1 フレーム遅れる。PR 2 で見つけた)。声の年齢を数える式が `min` になっていて、最初のブロックの
  あとも「鳴り始め」として扱われるため。止まる場所がブロックの区切り方で変わるので、再生と書き出しで
  音が食い違う (440Hz の正弦波で、山の高さの 6% の差)。これも `PATCHES` で直している (`min` → `max` の 1 語)。
  テスト「processに渡す長さを変えても同じ音になる」が確かめる
- サンプルの頭の長さは、1 ブロックより十分長くする。ノートを鳴らしたブロックの中は頭だけで鳴らすため、
  足りないと声がすぐ終わる。音を上げて鳴らすと速く読み進むので、その倍率ぶんも要る
- sfizz の開発は落ち着いている (最後のコミットは 2025-03)。止まった場合に備え、つなぎは
  `sampler.rs` の中に閉じ込めておく

## engine を作って分かったこと (2026-11-13、PR 2)

`bunri-audio` に engine とオフライン描画を足した。アプリ (Tauri の crate) からはまだ呼んでいない。

```rust
let mut engine = Engine::new(&song, &EngineConfig::default())?;   // 重い。音声スレッドの外で
let audio = render(&mut engine, &RenderOptions::default());       // 曲の頭から終わりまで + 余韻
audio.write_wav_file(path, WavFormat::Pcm24)?;
// 再生 (PR 3) は、同じ engine の process(left, right) を音声スレッドから呼ぶ
```

### 決めたこと

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 置き場 | 試作と同じ別の crate (`src-tauri/audio-engine`) のまま。上の「構成」を直した | Tauri 抜きでビルドとテストができる |
| ノートの位置 | ティック (1 拍 = 960) で受け取り、テンポと 1 小節目の位置 (いまのグリッドの `bpm` / `offsetSec`) でフレームにする。終わりは「始まり + 長さ」のティックから求める | 長さをフレームにしてから足すと、丸めが積み重なって隣のノートとの境目がずれる。画面のデータをティックにするのは PR 4 で、それまでは渡す側が `step` × 240 にする |
| テンポ | 曲に 1 つ | いまのプロジェクトがそうなっている。途中で変わるテンポは、要るようになったら足す |
| 楽器 | トラックごとに SFZ の場所を受け取る。楽器が無いトラックのノートは鳴らさない | カタログの id から場所を引くのと、「未指定はピアノ」は、素材が入る PR 5 で渡す側が行う |
| クリップ | デコード済みの音声 (モノラルかステレオ) をメモリで受け取る。engine と周波数が違えば、組み立てのときに一度だけ変換する | ブロックごとの処理が「重なる部分を足すだけ」になり、音声スレッドで補間もメモリの確保もしない |
| 周波数の変換 | 自作 (カイザー窓をかけた sinc、片側 64 交差)。低いほうのナイキストの 90% まで平坦、その上は約 -100dB。遅れを持たず、位置がずれない | 原曲と打ち込みを重ねるので、位置をフレーム単位で合わせたい。既製の crate は遅れの補正を自分で書くことになる |
| パン | いまの画面 (Web Audio の `StereoPannerNode`) と同じ決まり。ステレオの素材は中央でそのまま、モノラルの素材は中央で左右とも -3dB | 再生を Rust に移したときに音量が変わらない |
| ミュートとソロ | ミュートしたトラックは鳴らず、ソロが 1 本でも在ればソロだけ (画面の `audibleTracks` と同じ)。曲の長さは、鳴らないトラックも数える | 聞いた音と書き出した音を同じにする |
| 途中からの再生 | 始める位置をまたいでいるノートは、そこから鳴らし直す (いまの画面と同じ)。終わっていたノートは鳴らさない | ピアノやドラムでは、鳴らし直すとアタックが入る。気になるなら楽器の種類で分ける |
| 同じ高さの重なり | 同じ高さのノートが重なっているあいだは離さず、最後の 1 つが終わるところで離す | sfizz は「その高さを離す」としか受け取れず、先に終わったノートが、続いているノートまで止めてしまう |
| 余韻 | 曲の終わりまで書き出すときは、離したあとの響きが消えるまで続ける (上限は既定で 10 秒)。範囲を指定したときは、範囲ちょうどで切る | いまの書き出しは最後のノートの終わりで切れる。ピアノでは不自然 |
| 書き出しの形式 | WAV の 16bit / 24bit / 浮動小数 32bit。整数は範囲の外を端の値に切る | ディザはかけていない (16bit で書き出すときに要るかは PR 3 で決める) |

### 設計と変えたこと

- **置き場**: `src-tauri/src/audio/` ではなく、別の crate のまま (上の表)
- **クリップはディスクから読みながら鳴らさない。メモリに全部置く。** 素材 (数 GB) と違い、取り込んだ音声は
  1 曲ぶん (48kHz・4 分のステレオで約 90MB、ステム 4 本を足して約 460MB) なので載る。もっと長い音声を扱うように
  なったら、sfizz と同じ「頭だけメモリ」にする
- **sfizz への直しが 2 つになった** (「見つけた落とし穴」)

### 音声スレッドでの約束をどう守っているか

- `Engine::new` が、重いことをすべて済ませる (SFZ の読み込み、クリップの変換、ノートの並べ替え、作業用の
  バッファの確保)。`process` と `seek` は、メモリの確保・ロック・ファイルの読み書き・ログ出力をしない
- テスト `tests/realtime.rs` が、確保の回数を数えるアロケータに差し替えて、`process` と `seek` のあいだの
  確保と解放が 0 回であることを確かめる (数えられるのは Rust の側だけ。sfizz の中は見えない)
- `Engine` を捨てるとメモリの解放が起きる。曲を差し替えるとき (PR 3) は、古い engine を音声スレッドで捨てず、
  別のスレッドへ送り返す
- 音量・パン・鳴らすかは、再生中にも動かせる (`Engine::set_track_mix` / `set_track_audible`。画面からは
  ロックの無いキューを通る。PR 3)

### 測ったこと (MacBook Air、Apple Silicon、release ビルド)

| 項目 | 結果 |
|---|---|
| クリップの変換 | 4 分のステレオ (44.1kHz → 48kHz) を含む組み立てが 0.45 秒 |
| オフライン描画 | 上のクリップ + 正弦波の楽器のノート 11 個、240 秒を 0.31 秒 (実時間の約 770 倍)。ノートだけの 6.4 秒は 0.076 秒 (約 85 倍) |
| ブロックの区切り方による差 | 中のブロックが 64 / 100 / 128 / 256 フレームのとき、出力は 1 ビットも変わらない。長さが 4 の倍数でないブロック (1、7、77 など) が混ざると、サンプラーの音に山の高さの 0.04% (約 -68dB) の差が出る |

### テストの素材

リポジトリに入れられる小さな素材を、テストの中で作る: 正弦波の WAV を A4 に割り当てた SFZ
(楽器)、決まった並びの雑音 (クリップ。位置がずれたり左右が入れ替わったりすれば一致しなくなる)。
本物の楽器 (Salamander など) は使わない。`examples/render_sfz.rs` に SFZ (と、重ねる WAV) を渡すと、
手元の素材で同じ engine を通した WAV を作れる。

## 再生を Rust に移して分かったこと (2026-11-14、PR 3)

デスクトップ版の再生・停止・位置・区間ループ・メトロノーム・録音前のカウント・鍵盤の試聴を、Rust の engine が
cpal で鳴らすようにした。ブラウザでは今までどおり Web Audio。

```
画面 (lib/engine.ts の AudioEngine)
  └─ lib/native-audio.ts ── Tauri command (audio_*) ──► src-tauri/src/audio.rs
                          ◄── Tauri event (audio://position) ──┘      │ ロックの無いキュー (rtrb)
                                                                       ▼
                                             音声スレッド (cpal のコールバック): transport → engine
```

### 決めたこと

| 項目 | 決めたこと | 理由 |
|---|---|---|
| ノートの音 | 楽器の素材が入る PR 5 まで、Rust の側でも三角波で鳴らす (`Instrument::Tone`、`tone.rs`)。ノートの在るトラックに、渡す側 (`audio.rs`) が当てる | 楽器が無いトラックのノートは鳴らない決まり (PR 2) のままだと、再生を移した時点でノートが無音になる |
| クリップの音声の渡し方 | 画面がデコードした PCM (Float32) を、4MiB ずつに分けて生のバイト列で送る (`audio_clip_put`)。Rust はファイルを読まない | 録音は webm (opus) で、Rust の側に読めるデコーダが無い。波形の表示と同じデコード結果を鳴らせる。「分かっていない点」に在った問いの答え |
| 曲の内容を渡す時機 | 再生を始めるとき (`audio_set_song`)。前と同じ内容なら送らない。再生中の編集は、次に鳴らし直すまで音に出ない | いまの Web Audio の再生が、`play()` の時点の内容を予約するのと同じ。画面は編集のたびに Rust へ知らせなくてよい |
| 再生中にすぐ効かせるもの | トラックの音量・パン・鳴らすか (5ms の直線で移す)、メトロノームの入/切、鍵盤の試聴 | フェーダーを動かして「ぷつっ」と鳴らないように |
| 速度 (練習画面) | 画面が時間軸を変換して渡す (テンポに速度を掛け、1 小節目の位置を区間の頭から測り直し、伸ばした音声を区間の頭に置く)。Rust は速度を知らない | engine に速度の概念を足さずに済む |
| 位置の知らせ | 音声スレッドが「ブロックの頭の位置と、そのときの時刻」をロック無しで書き (seqlock)、別のスレッドが 33ms ごとに event `audio://position` で送る。画面は、event のあいだを経過時間で補う (壁時計どうしで比べる。画面は `Date.now()`) | `getCurrentTime()` を同期のまま保つ。`performance.now()` は、スリープのあいだ進まないので使わない |
| 失敗したとき | Rust の呼び出しがどこかで失敗したら、そのセッションのあいだ Web Audio に切り替え、再生中なら同じ位置から鳴らし直す。鳴らし始めて 2 秒のあいだに位置の event が 1 つも届かないときも、失敗として扱う | 出力デバイスが無い機械や、想定していない壊れ方でも、音が出ないままにしない |
| Web Audio に戻す抜け道 | `localStorage` の `bunri.audioBackend` を `web` にして読み込み直す | 開発中の切り分け用 |
| つなぎ目 | 曲の音が不連続になるところ (途中からの鳴らし始め、区間の頭と終わり、再生中の停止・鳴らし直し・曲の差し替え) は 4ms の直線で上げ下げする。曲の頭 (0 秒) からのループでない再生は上げない | 「ぷつっ」を消す。頭ちょうどに在るアタックは弱めない |
| バッファ | 256 フレーム (48kHz で 5.3ms) を頼み、受け付けないデバイスでは既定の長さで開く | 鍵盤を弾いてから音が出るまでの遅れを詰める |
| 出力デバイスが使えなくなったとき | Rust は、その再生の event を「止まった」で 1 回送る。画面は、頼んでいないのに止まったと分かったら、止まった位置から鳴らし直す (10 秒に 3 回を超えたら Web Audio に切り替える)。Rust は、次の鳴らす指示 (`audio_init` / `audio_set_song` / `audio_play` / 鍵盤の試聴) で開き直し、最後に渡された曲を渡し直す | 再生中にイヤホンを抜いても、「再生中」の表示のまま音も位置も止まった状態にしない。周波数が変わりうるので、transport と engine は作り直しになる |
| 録音前のカウントの終わり | event に、カウントが終わるまでの残り (秒) を入れる。画面は、次の event を待たずに「カウントが終わった」と分かる | event を待つと、最大 40ms ほど (バッファ + 33ms + IPC) 遅れて知ることになり、そのあいだに弾いた 1 拍目の音を、MIDI のリアルタイム録音が捨てる |
| 画面が無くなったとき | 再生を頼んだ窓が閉じたら、Rust が音を止める。画面を読み込み直したときは、出力を開いた直後に、画面が前の再生と試聴を止める | Web Audio の音は画面と一緒に消えるが、Rust の音は消えない |
| どちらで鳴らしているかの印 | 画面の根の要素に `data-bunri-audio="native"` か `"web"` を付ける (デスクトップ版だけ) | 本物の窓のテストが、途中で Web Audio に切り替わっていないことを確かめる。切り替わっても再生位置は進むので、印が無いとつなぎの不具合を見逃す |
| 書き出し・録音・デコード | 画面側 (Web Audio / `MediaRecorder`) のまま | 仮の音のあいだは、書き出した音と聞いた音がほぼ同じ。楽器の音が入る PR 5 で、書き出しを Rust のオフライン描画に移す |
| MIDI 鍵盤の試聴 | 画面が `audio_live_note` を呼ぶ (MIDI 入力 → 画面 → Rust)。Rust の中で MIDI 入力から engine へ直接渡すことは、していない | 録り方 (ステップ入力・リアルタイム録音) を画面が決めているため。遅れが気になるようになったら、楽器の音が入ってから測って決める |

### いまの画面 (Web Audio) と音が違うところ

- **ノートの消え方。** Rust はノートの終わりで離して 60ms で消える。Web Audio は、ノートの中で
  `min(0.15 秒, 長さ × 0.3)` かけて下げ、終わりで 0 になる。Rust のほうが終わりぎわが大きく、60ms 長く鳴る
- **またいでいるノートの鳴らし直し。** 途中からの再生・区間の頭・鳴らす側への切り替えでは、10ms の立ち上がりを付ける
  (Web Audio は、いきなり山の高さで始める)
- **同じ高さの重なったノート。** 最後の 1 つの終わりでまとめて離す (PR 2 の決まり)。Web Audio はノートごとに終わる
- **再生中のミュート解除・ソロ。** Rust ではすぐ音に出る。Web Audio では、`play()` の時点で鳴らさなかったトラックは、
  鳴らし直すまで出ない
- 三角波は帯域制限していない (倍音が 1/n² で減るので、折り返しは小さい)。仮の音なので、そのままにしている

### 作り

- スレッドは 3 つ。音声スレッド (cpal のコールバック。`Transport` と engine を持つ)、command のスレッド
  (重いものは `spawn_blocking`)、位置を送るスレッド (止まっているあいだは眠る)
- 画面 → 音声スレッドは rtrb のキュー。古い engine は別のキューで送り返し、音声スレッドの外で捨てる
- 位置を送るスレッドが眠るのは、「止まっていて、頼まれた再生も待っていない」ときだけ。再生を頼まれたら、音声スレッドが
  その再生を始めるのを見るまで待つ (最初のコールバックが遅いデバイスでも、event を出し損ねない。上限 5 秒)
- 片付けは 2 か所に要る。窓が無くなったとき (`WindowEvent::Destroyed`) と、アプリの終わり (`RunEvent::Exit`)。
  ほかの窓が残っていると、後者は走らない
- クリップの音声は 1 本につき 1 つだけ持つ。周波数が出力と違えば最初の `audio_set_song` で一度だけ変換し、
  次からは同じ `Arc` を使い回す (曲を渡すたびに変換し直さない)
- cpal 0.18 の `Stream` は、どの OS でも `Send + Sync` (0.16 までは mac で `Send` でなかった)。専用のスレッドは要らない。
  ストリームは止まった状態で返るので `play()` が要る
- Tauri 2.12 では、JS の `invoke(cmd, Uint8Array, { headers })` が、生のバイト列と HTTP ヘッダで届く
  (`tauri::ipc::Request` で受ける)。`ipc:` の経路が使えないときは数の配列の JSON になるので、どちらでも受ける
- 仮の音は声 64 (トラックごと)、試聴は声 32、クリックは 4。足りなければ、離したあとのいちばん古い声から使い回す

`cargo run --release -p bunri-audio --example output_check` (本物の出力デバイスを開いて transport を 3 秒回す。
出力に 0 を掛けるので音は出ない)。鳴らした曲は、三角波の 4 和音・雑音のクリップ・メトロノーム・試聴 1 音。

| 項目 | 結果 |
|---|---|
| デバイス | 内蔵スピーカー 48000Hz / 2 チャンネル / f32。開くのに 104ms |
| バッファ | 256 フレームを頼み、588 回のコールバックすべてが 256 フレーム (5.33ms) |

### 確かめ方

- 音と再生の状態は Rust のテスト (`tests/transport.rs`・`tests/tone.rs`)。本物のデバイスは使わない。
  `tests/realtime.rs` が、transport の `process` も確保・解放をしないことを確かめる
- command は、偽の窓 (`tauri::test`) とデバイスを開かない偽の出力で、IPC の口から確かめる (`src-tauri/src/audio.rs` のテスト)
- 画面の側は Vitest (`web-ui/src/__tests__/native-audio.test.ts`。`__TAURI__` を偽物にする)。`make e2e` は Web Audio の経路だけを通る
- 窓ごと確かめるのは `make e2e-desktop` (環境変数 `BUNRI_E2E_AUDIO_SILENT=1` で、スピーカーから音を出さない)。
  出力デバイスを開けた機械では、再生のあとも Rust の engine で鳴らしていること (`data-bunri-audio="native"`) まで見る

### 受け入れていること

- **メモリ。** クリップの音声を Rust にも写すので、画面の `AudioBuffer` と同じ大きさがもう 1 つ要る (4 分のステレオ 1 本で約 92MB、
  原曲とステム 4 本で約 460MB)。送るのは、クリップを足したとき・プロジェクトを開いたとき。プロジェクトを開き替えても、
  次に再生するまで、前の曲の engine と音声が Rust に残る。困るようになったら、開き替えたときに空の曲を渡して捨てる
- **遅れの値。** 画面は、最初に出力を開いたときの値 (`audio_init`) を持ち続ける。既定のデバイスが途中で替わっても
  (Bluetooth のイヤホンなど) 変わらないので、MIDI のリアルタイム録音の位置の補正がずれる。録音の画面で手で直せる

### 確かめられていないこと

- **本物の窓での動作と、耳で聞いた音。** Rust の側と画面の側は、それぞれのテストでしか確かめていない
  (`make e2e-desktop` を回していない)
- 本物のデバイスの抜き差し・Bluetooth への切り替えでの開き直し、f32 / 2 チャンネル以外のデバイス
- 大きいクリップ (4 分のステレオで約 92MB) を送るのにかかる時間
- 配布物 (`tauri build`) での動作

## 分かっていない点

- 楽器とクリップの音量の釣り合い。sfizz は既定の音量が -7.35dB (`Defaults.h` の `globalVolume`) で、
  山の高さ 0.5 の正弦波 (モノラル) を強さ 127 で鳴らすと、左右とも 0.13 (-11.5dB) で出た。クリップは
  そのままの大きさで出るので、楽器が小さく聞こえるかもしれない。本物の楽器を入れる PR 5 で、
  原曲と並べて聞いて決める
- ブロックの長さが 4 の倍数でないときに出る、サンプラーの音のわずかな差 (-68dB) の原因。sfizz の中の
  4 個ずつまとめて計算する部分と、端数の部分の違いだと見ているが、確かめていない
- 同じ楽器を複数のトラックで使うと、トラックごとに sfizz を 1 つ作るので、サンプルの頭を置くメモリも
  トラックの数だけ要る (Salamander で 1 つ約 150MB)。困るようになったら共有を考える
- 曲を渡すたびに engine を組み立て直す作りで、楽器の素材が入ったあとも間に合うか。いまは仮の音とクリップ (変換済みを
  使い回す) だけなので軽い。SFZ はトラックごとに読み込み直しになる (2 回目以降は 0.08 秒) ので、PR 5 で測る
- MIDI 鍵盤を弾いてから音が出るまでの遅れは、耳で確かめていない (バッファ分は 1.3〜2.7 ms。
  ほかに音声デバイス側の遅れが乗る)
- 低い性能の機械での余裕 (いま測ったのは Apple Silicon のみ。Intel mac は対象外)
- アンプの模擬に使うキャビネットのインパルス応答の出どころ (自由なライセンスのものか、自作か)
- 画面側の作り: ドラム用の打ち込み画面 (ピアノロールとは別にするか)
- **配布する前に、sfizz と依存のライセンス文を同梱する (まだしていない)。** PR 3 から、アプリが sfizz を
  リンクしている。cpal (Apache-2.0) と rtrb (MIT / Apache-2.0) も増えた。依存はすべて制限の緩いもの
  (BSD-2/3、MIT、Apache-2.0、Boost、zlib、WTFPL、パブリックドメイン) で、自分のコードを公開する義務は無い
