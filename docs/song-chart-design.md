# 楽曲カルテ（第1層）設計

bunri を「生成しないAI統合DAW」にするための第1層の設計。2026-08-29 の設計セッション（grilling 6ラウンド、29決定）で確定した内容。

## 製品方針

AIは**生成器ではなくアシスタント**である。取り込んだ楽曲を教材として、ユーザー自身が再現できるよう導く。

原則はひとつ：**DSPが事実を出し、LLMは言語化だけをする。LLMは音符を1つも出力しない。**

これにより「生成しないアシスタント」が構造的に保証され、同時にハルシネーションも潰れる。LLMが「Cメジャーですね」と言うとき、それは推測ではなくカルテの読み上げになる。

### 3層構成

| 層 | 名前 | 内容 | LLM |
|---|---|---|---|
| 第1層 | 楽曲カルテ | 解析結果の構造化データ | 不使用 |
| 第2層 | 再現ガイド | 「こう作れば再現できる」の説明 | 使用 |
| 第3層 | 差分コーチ | ユーザーの打ち込みと原曲の差分指摘 | 使用 |

**第3層が本命の差別化点。**第1層・第2層だけでは Moises 等の既存製品と勝負にならない。

### 競合状況（2026-08 調査時点）

市場は3つに割れており、bunri の狙う位置はどれにも埋まっていない。

- **分離・耳コピ系** — Moises、RipX DAW、LALAL.AI、Audelta、SpectraLayers。Moises は分離＋キー/コード検出＋メトロノームで「曲を覚える」層を押さえている。RipX はノート単位のスペクトル編集まで踏み込み、機能的に bunri のコアに最も近い。**いずれも「なぜそうなっているか」を説明せず、ユーザーの再現を評価もしない。**
- **生成系** — Suno、LANDR Composer、MIDI Copilot、ChordChord。bunri が明確に否定した方向。
- **チャット型AI DAW** — WavTool、LIA、Soundverse。自然言語対話はあるが**全て生成側**で、「取り込んだ楽曲を教材にする」発想はない。

空白地帯は「①の解析能力 × ③のAI対話 を、生成ではなく評価と指導に振った領域」＝第3層。

リスク：参入障壁は技術ではない（Demucs も Basic Pitch もオープンソース）。堀になるのは「解析データをLLMに読ませて的確な指導をさせるプロンプトと評価の設計」で、模倣可能だが蓄積が効く。

## 設計上の急所

第1層を設計するうえで、崩れると全体が無意味になる点。

### グリッドが崩れるとカルテ全部が崩れる

BPM検出が倍/半分になると、コードもセクションも全部ずれる。しかも初心者はそれが間違いだと気づけない。「知識がない人を助ける」という目的と正面から衝突する。

対策：
- 倍/半分エラーの検証を検出側で行う（仕組み・測った精度・分かっている弱点は [grid-estimation.md](grid-estimation.md)）
- **波形＋ビートグリッド重畳の確認・補正UI を必須とする。**数値入力だけでは初心者は 128 と 64 のどちらが正しいか判断できない
- 実測ビート列 `beat_times_sec` を持ち、テンポ揺れがあっても秒↔小節・拍の変換が正確に保たれるようにする

### ハイライトには安定した参照子が要る

アシスタントの出力形式は「説明＋該当箇所のハイライト」。LLMが画面上の位置を機械可読に指せる必要がある。

対策：カルテの時間参照は**全て小節・拍の絶対位置**（`{"bar": 17, "beat": 1}`）。内部IDはユーザー編集で壊れるため使わない。

### プロンプトキャッシュにはバイト安定性が要る

「1曲のカルテに対してユーザーが何十回も質問する」使われ方になるため、カルテ＝安定した長いプレフィックスとしてプロンプトキャッシュが効く。キャッシュはプレフィックスのバイト完全一致が条件。

対策：
- `json.dumps(..., sort_keys=True)` でキー順を固定
- numpy float をそのまま入れず、全て `round()` で Python 型に落とす
- 解析日時・UUID・一時ファイルパスをカルテ本体に含めない

### 断定しないことが初心者向けの正解

嘘のラベルを自信満々に出すのは、初心者向けアシスタントとして最悪の失敗モード。全項目に確信度を持ち、低確信度は「検出できませんでした」と明示する。

## 第1層 v1 の仕様

### パイプライン

**速報のみ。ステム分離は使わない。**原曲ミックスのみを解析し、数秒〜十数秒で返す。

Demucs 6ステム分離（数分）を含む詳細解析は第2弾に送る。初心者が最初に触る機能が「5分フリーズ」では死ぬため。

### 解析範囲

| 項目 | 内容 |
|---|---|
| グリッド | BPM / ダウンビート / 拍子 / 実測ビート列 |
| キー | Krumhansl-Schmuckler によるキー推定 |
| コード | 拍単位で検出し同一コードを結合。三和音＋7th。ディグリー表記を併記 |
| セクション | 区間検出のみ。ラベルは提案に留める |
| ミックス | **曲全体の特性**（ラウドネス・ステレオ幅・残響・帯域分布） |

ミックスについて：ステム分離が無いため「ステム別のパン」は物理的に出せない。代わりに曲全体の特性を出す。初心者にとってはこちらの方が価値が高い（「なぜ市販曲は自分のミックスより良く聞こえるのか」に答えられる）。ステム別は第2弾。

### 各項目の決定

| 項目 | 決定 | 理由 |
|---|---|---|
| 拍子 | ユーザーがセレクトで選択（既定4/4）。自動検出しない | 自動検出は精度が実用に届かず、外れると初心者を破壊する。グリッド補正UIにセレクトを足すだけならコストゼロ |
| コード解像度 | 拍単位で検出し同一コードを結合（1小節に複数コード可） | J-POPは1小節2コードが頻出。1小節1コード固定では進行が半分潰れる |
| セクションラベル | `suggested_label` として提案のみ。`label` はユーザー確定まで null | 自動ラベルは洋楽・インストで簡単に崩れる。嘘を断定しない |
| 確信度の表示 | 「確実 / たぶん / 自信なし」の3段階。生値はカルテに保持する。LLM にも同じ3段階で渡す（2026-11-11 に変更。それまでは生値を渡していた） | 初心者に 0.71 は意味がない。LLM に生値を渡して段階に直させると、言い間違えた（[reproduction-guide-design.md](reproduction-guide-design.md) の「モデルと思考の深さの比較」）。コードで直せば、画面の表示と必ず一致する |
| 低確信度の扱い | 項目単位で欠落を許し「検出できませんでした」と明示 | 間違った値に「自信なし」を貼っても初心者は結局信じる。全体エラーはドラムループ等の有効なケースを捨てる |
| 検出感度 | UIに露出しない。既定値固定 | 初心者は感度を動かしても何が良くなったか判断できない |
| 編集可能範囲 | グリッド補正のみ。コード・セクション・キーは読み取り専用 | 結果の修正は間違いに気づける中級者以上の機能。第3層で開放する |
| 波形ピーク | バックエンドで生成しカルテと共に返す | カルテ生成時に既に音声をメモリに載せているのでコスト実質ゼロ。フロントで63MB以上をデコードさせない（低スペックPC前提） |
| 用語解説 | Python側にハードコード辞書。キー＋言語マップ構造 | 用語定義は曲によらないためLLMに毎回書かせるのは無駄で表現も揺れる。Python側ならLLMにも同じ辞書を渡せて説明が食い違わない |
| ツールチップ | 全要素に義務化。用語の解説を、要素のそばのツールチップ（`components/Tooltip.tsx`）に出す | |
| 多言語 | `{"key": {"ja": "..."}}` の器を切り、v1は日本語のみ | 競合は全て英語圏。後から入れると全面改修になる |

## 永続化

### 2層構成

| 層 | 中身 | 形 |
|---|---|---|
| ドキュメント層 | 楽曲プロジェクト（カルテ・将来はトラック/ノート/進捗） | `.bunri` = SQLiteベース単一ファイル |
| アカウント層 | ユーザー情報・認証・課金・同期 | RDB（将来、プロダクト化時） |

CLIP STUDIO の `.clip`、Ableton の `.als` と同じ思想。SQLiteに直結せずリポジトリ抽象の背後に置き、差し替え可能にする。

### v1の範囲

**スキーマ確定＋カルテの作成/読込のみ。**既存 `projects/*.json` とは並存し、移行は第2弾。

スキーマを今確定させる目的は「カルテの置き場所を二度移さないこと」であり、まだ設計していないものの器を先に切ることではない。投機的スキーマは実際に作るとき必ず作り直しになる。

| 項目 | 決定 |
|---|---|
| スキーマ範囲 | カルテ関連テーブルのみ |
| バージョニング | `bunri_meta` テーブルに `format_version` / `app_version` / `created_by`。**前方互換**（未知のテーブル・列は無視） |
| 1ファイルの粒度 | **1ファイル1曲** |
| 音声データ | 選択式で**既定は内包** |
| v1のUI露出 | 出さない。カルテ生成時に裏で自動生成 |

音声内包を既定にする理由：Ableton 等は既定が外部参照だが、bunri の対象ユーザーには逆にすべき。「ファイルが見つかりません」は初心者が自力で対処できない失敗で、原因が数週間前のフォルダ移動だったりする。

保存UIについて：`.bunri` をUIに出すと「プロジェクトを保存」と2つ並び、解析ボタンで否定したのと同じ混乱が起きる。v1では静かに実体化させ、第2弾でトラック・ノートを寄せた時点で初めてユーザーに見せる。（2026-11 に寄せて見せた。下の「プロジェクトの保存」。カルテの API が作る `results/charts/*.bunri` は、いまも作業用のファイルとして裏で作る）

### プロジェクトの保存（.bunri v2。2026-11 に実装）

第2弾として、トラック・ノートを `.bunri` に寄せ、利用者に見せた（ヘッダの「保存」「開く」）。1 ファイル 1 曲のまま、
カルテの表はそのまま使い、表を足した。形式の版は `format_version` 2.0（v1 の bunri は「新しい形式」として断る）。

| 表 | 中身 |
|---|---|
| `bunri_meta` | `format_version` 2.0、`app_version`、`document`=`project` |
| `project` | 名前・テンポ・拍子・1 小節目の位置（`grid_offset_sec`）・作成/更新の時刻・UUID（1 行） |
| `project_tracks` | 並び順・名前・役割（song/part/practice）・パート・練習の相手（並びの番号）・音量・パン・ミュート・ソロ・お手本の有無・`extra`（JSON。将来の項目を足す口） |
| `project_notes` | トラックごとのノート。`kind` が `notes`（打ち込み）か `reference`（お手本） |
| `project_clips` | クリップの位置・長さ・名前と、音声のハッシュ |
| `audio_blobs` | 音声。鍵は元のバイト列の SHA-256（同じ音声は 1 つだけ。原曲のクリップとカルテの元音声も共有する）。整数 PCM（16/24/8 bit）の WAV・AIFF は FLAC（`codec=flac`。サンプルはビット単位で一致）、それ以外（MP3・M4A・浮動小数の WAV・録音の webm）は元のまま（`raw`） |
| `project_state` | 節ごとの状態（JSON と版）。`learn`（重ねるお手本・差分チェックの組と最後の結果と比べたノート・開いていたタブとトラック）、`chart_view`（カルテの ID と波形のピーク）、`practice`（練習画面。下の「状態の節」） |
| `learning_history` | 学習の記録（[coach-diff-design.md](coach-diff-design.md)「学習の記録」） |
| `cached_results` | ガイドと差分の説明の写し（種類・鍵・中身）。開くと保存の置き場（`results/guide|coach/cache/`）へ戻すので、別の PC で開いても Claude を呼ばずに出る |
| カルテの表（v1 と同じ） | `chart_audio` に `audio_hash` 列を足し、元音声は `audio_blobs` を指す |

- **v1 からの移行**: `bunri_file.migrate` が表と列を足し、`chart_audio.data` を `audio_blobs` に移す。開くときは作業用の写しに対して行い、利用者のファイルは書き換えない。カルテだけのファイルは「カルテと原曲のトラック 1 本」のプロジェクトとして開く
- **前方互換**: 知らない表・列・節は読まない。開いて保存し直しても、知らない節は消さずに残す（画面の `unknownSections`）
- **何を保存するかの大もと**: 画面の元に戻すの控え（`web-ui/src/lib/project-snapshot.ts`）。保存のために 2 つ目の一覧を作らない。控えに無い音声・カルテ・学ぶ流れの状態・記録を、`lib/project-file.ts` が足す
- **音声の持ち方**: 画面は、デコードしたときの元のバイト列を覚えておき（`lib/audio-sources.ts`）、それを送る。開き直すと同じバイト列をデコードするので、同じ音に戻る。元のバイト列が無い音声は 32 bit 浮動小数の WAV で送る（FLAC にならないので大きい）。送るのは sidecar が持っていない音声だけ（保存し直しでは、開いている写しから同じハッシュの音声をそのまま写すので、送らない）
- **エフェクトの設定**: 持っていない。エフェクトは音声に掛けて差し替える作りなので、掛けた結果の音声がクリップとして入る

**状態の節（練習画面などが足す口）**: 画面で `registerProjectSection('practice', { version, save, load })` を登録すると、保存のときに
`save()` の値が `project_state` の `practice` 行に版つきで入り、開いたときに `load(値)` が呼ばれる（無ければ `null`）。状態を変えたら
`useDaw().touchProject()` を呼ぶと、保存していない変更の印が付く。形を変えたら `version` を上げ、`load` で古い版を読む。sidecar は中身を見ない。

練習画面の節 `practice`（版 1。`web-ui/src/lib/practice-project.ts`、形は `lib/practice.ts` の `practiceToSection` / `practiceFromSection`）:
`part`・`track`（パートと練習のトラックの並びの番号）、`loop`（`startBar` `endBar` `enabled`）、`speed`、`listen`、`showGhost`、`input`。
練習画面を一度も開いていなければ入れない。開いたときは設定だけ戻し、**練習画面は開かない**（アレンジで開く。開いた直後は
音声の無いクリップの知らせなどプロジェクト全体を見てほしいこと、練習画面を開くと MIDI の接続や速度を変えた音声の用意が
始まるので、利用者が何もしないうちにそれをしないこと。区間はタイムラインの目盛りに出る）。番号が範囲の外・お手本の無い
トラックを指していれば、状態を持たない。速度・聴く・入力の知らない値は既定（100% / 両方 / マウス）に直す。
保存していない変更の印は、利用者が区間・速度・聴く・お手本・入力を変えたときだけ付く（開く・閉じる・再生では付けない。
MIDI がつながらずに画面がマウスへ戻したときも付けない）。

**測った大きさと時間**（3 分・44.1 kHz・ステレオ・16 bit の原曲 WAV と 6 パートの WAV、お手本 1,400 ノート × 6、合成音。2026-11-12、M シリーズの Mac）:

| 音の中身 | WAV の合計 | .bunri | 初回の保存（sidecar 側） | 保存し直し | 写しを開く（音声の転送を除く） |
|---|---|---|---|---|---|
| 音程のある合成音（圧縮が効く側） | 222 MB | 123 MB（55%） | 1.4 秒 | 0.14 秒 | 0.01 秒 |
| 雑音の多い合成音（効かない側） | 222 MB | 165 MB（74%） | 1.7 秒 | 0.20 秒 | 0.01 秒 |

実際の曲の FLAC はこの間に収まることが多い（市販曲で 55〜70%）。原曲が MP3 なら原曲ぶんは元のまま（3 分で 5〜7 MB）なので、さらに 20 MB ほど小さい。
保存はジョブの仕組み（`?async=1`）を使わない。重い処理は同時に 1 つなので、パート分離の最中に保存できなくなるため。FastAPI のスレッドで
動かし、画面は待たずに操作でき、ステータスバーに「保存しています…（音声 3/7）」を出す。

**sidecar はデータ置き場の外を読み書きしない**: 保存は `work/<token>.bunri` に書き、利用者が選んだ場所へ写すのはデスクトップ版では Rust
（[desktop-architecture.md](desktop-architecture.md)「プロジェクトのファイル」）、開発用のブラウザ起動では `projects/` へ写す。

## UI

- **DAW画面のファイルタブに解析ボタンを1つに統合。**（2026-11 に、左パネルの「学ぶ」タブの「曲を取り込む」へ移した。取り込むと原曲のトラックも作る）押すとまず数秒でカルテ、必要なら「さらに詳しく」でステム分離（第2弾）
- カルテの表示先は左パネルの「カルテ」タブ。波形＋ビートグリッド補正UIは横幅が要るためモーダル
- 第2弾の詳細解析は**ゴースト表示が既定**、「お手本をノートとして取り込む」で編集可能ノートに変換（2026-11 に実装。当時の呼び名は「答えを取り込む」。画面のことばは [ui-terms.md](ui-terms.md)）
- 取り込んだ曲のテンポ・拍子・1 拍目の位置は、そのままピアノロールのグリッドになる。カルテの小節番号とピアノロールの小節番号が同じ時刻を指すように（[coach-diff-design.md](coach-diff-design.md) の「カルテとピアノロールの小節番号」）

ゴースト表示について：現状の完全解析は解析結果を全トラック・全ノート自動配置する。これは答えを全部見せる挙動で、「自分の力で再現する」という目的と正面から衝突する。**これを崩すと第3層の差分コーチが原理的に成立しない**（比較対象が最初から答えそのものになるため）。

## モジュール構成

既存のフラット構成に合わせる。

API：

- `POST /api/chart` — 音声 → カルテ。`chart_id` を返し `.bunri` を生成
- `POST /api/chart/regrid` — `chart_id` ＋補正後のBPM/オフセット/拍子で再計算

## デスクトップアプリ移行への布石

将来 Web からデスクトップアプリへ移行する予定。第1層で対応するのは**パス解決の一点のみ**。

- 新規モジュールは `audio_utils.results_dir()` 経由でパスを解決する。既存モジュールは触らない
- 署名済みデスクトップアプリは実行ファイルの隣に書けないため、いずれ OS のアプリデータディレクトリへ移る

第2層以降で対応が必要になるもの：APIキーの持ち方（配布アプリに同梱できないため、設定UIとセキュアストレージが要る。当時の `music_assistant.py` は import 時に `os.getenv` しており、起動後に設定したキーを拾えなかった）、torch/demucs のバンドル戦略（数GB規模）。
